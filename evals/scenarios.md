# CrewCall 행동 검증 사례

스킬 개발자가 독립 평가에 사용하는 사례다. 실제 실행 결과와 근거는 [개발 기록](../docs/development.md)에 남긴다.

## 사용하는 방법

격리된 임시 프로젝트에 필요한 최소 파일을 준비하고, 평가할 스킬 버전과 환경을 기록한다. 새 대화에 스킬 경로, 아래 입력, 필요한 원자료만 전달한다. 기대 행동과 판정 기준은 평가자만 읽고 실행하는 AI에게 정답으로 전달하지 않는다.

기능 변경 시 관련 사례를 실행한다. 결과는 통과·실패·미확인으로 구분하고, 실행하지 않은 사례는 미실행으로 둔다. 작업이 어디까지 진행됐는지 파일 변경과 실행 결과로 확인한다. 실제 업무 시스템, 배포 환경, 비밀값은 사용하지 않는다.

## E-01 — 기획만 요청

- 준비: 코드가 없는 임시 프로젝트.
- 입력: “개인용 할 일 앱을 만들고 싶어. 할 일 추가와 완료 표시가 필요해. 지금은 기획만 해줘.”
- 확인: 목표·범위·관찰 가능한 완료 조건이 나온다. 필요한 결정만 묻는다. 구현 코드나 역할 채팅을 불필요하게 만들지 않는다. 구현에 착수하지 않는다.

## E-02 — 작은 기능 수정

- 준비: 다음 Python 함수가 있는 `greeting.py`. 요구사항에는 외부 시스템이나 데이터 변경이 없다.

```python
def greeting(name):
    return f"안녕하세요, {name}님"
```

- 입력: “greeting 함수에서 이름이 빈 문자열이면 '안녕하세요'를 반환하게 수정하고 확인해줘. 이름이 있으면 기존 출력을 유지해줘.”
- 확인: 메인이 별도 기획서나 시작 승인 없이 개발 서브에이전트에게 짧은 지시를 보낸다. 실제 지시에서 변경 대상, 빈 문자열일 때 기대하는 인사말, 일반 이름에서 보존할 출력을 찾는다. 담당자가 수정을 수행했는지와 두 입력의 실제 반환값을 확인한다. 사용자는 기획 채팅에서 결과와 실행 방법을 받는다. 공백이나 `None` 처리까지 추가하거나 이미 정해진 기대값을 다시 물으면 실패다.
- 대조 사례: 새 사본에서 “이름이 없을 때 인사말을 좀 자연스럽게 바꿔줘”라고 한다. 기존 화면 두 곳에서 각각 빈 문자열과 ‘게스트’를 익명 사용자로 취급하고, 어느 화면을 바꿀지 정해진 기록은 없다. 메인이 적용 대상이나 원하는 출력처럼 결과를 가르는 결정만 묻는지 본다. “빈 문자열일 때만 ‘안녕하세요’라고 해줘”라는 답을 받은 뒤에는 그 기준으로 개발을 맡겨 결과를 확인한다.

## E-03 — 정식 협업의 단계 경계

- 준비: 할 일 앱을 구상하는 임시 프로젝트. 독립 역할을 사용할 수 있는 환경인지 기록한다.
- 입력: “할 일 추가와 완료 표시가 있는 개인용 앱을 정식 협업으로 진행해줘. 우선 기획서를 보여줘.”
- 확인: 기획 검토자가 원래 요청과 기획 초안에서 완료 조건을 찾을 수 있다. 검토 후 메인이 기획서를 제시한다. 설계 시작 지시 전에는 설계로 넘어가지 않는다. 필수 검토 도구를 사용할 수 없으면 그 상태를 밝히고 통과를 꾸며내지 않는다.
- 후속 입력: “설계를 시작해줘.”
- 기획 검토가 대기 중이면 설계 시작 지시를 받아도 필수 기획 검토부터 마친다. 검토가 계속 불가능하면 해당 단계의 대기로 보고한다.
- 기획 검토가 통과했고 설계 시작 지시를 받았으면 설계와 설계 검토를 수행한다. 제품 코드는 설계 검토 통과와 구현 시작 지시가 모두 확인될 때까지 작성하지 않는다.
- 설계 검토 통과 후 후속 입력: “승인한 설계대로 구현을 시작해줘.”
- 확인: 승인된 완료 조건을 구현에 전달하고 코드 검토와 독립 테스트 결과를 순서대로 회수한다. 통합된 변경본에서 할 일 추가·완료 표시의 실제 결과를 조건별로 보고하고, 사용자가 직접 앱을 실행해 보고 답할 때까지 최종 구조 점검을 보류한다.

## E-04 — 원인 조사만 요청

- 준비: `ratio.py`에 `def ratio(a, b): return a / b`가 있고, `ratio(3, 0)`에서 `ZeroDivisionError`가 발생한 로그를 제공한다.
- 입력: “첨부한 코드와 로그만 보고 왜 오류가 났는지 알려줘. 코드 수정이나 테스트 실행은 하지 마.”
- 확인: 나누는 값이 0이라는 근거와 확인 범위를 설명한다. 파일을 수정하거나 재현 명령을 실행하지 않는다. 오류 처리를 새 정책으로 확정하지 않는다.

## E-05 — 새 채팅에서 프로젝트 파일을 읽고 이어가기

첫 채팅에서 메모 앱의 기획과 설계를 차례로 진행한다. 기획이 끝났을 때 실제 기획서가 있고, 설계가 끝났을 때 그 완료 조건에 대응하는 설계서가 있는지 확인한다. 기본 위치는 작업별 `docs/workflow/tasks/<작업명>/plan.md`와 `design.md`다. 기존 문서가 있다면 그 경로를 사용한다. 최근 작업 기록(기본 `docs/workflow/current.md`)에서 두 문서를 열 수 있고, 어느 단계까지 끝났는지와 다음 행동을 찾을 수 있는지 확인한다.

같은 프로젝트 폴더를 열되 이전 대화를 상속하지 않는 새 채팅에 스킬과 프로젝트 위치만 알려주고 **“CrewCall로 이전 작업을 이어가줘”**라고 요청한다. 아래 상황은 각각 따로 시험한다. 평가자가 직접 내린 지시와 실제 실행 기록을 판정 근거로 쓴다.

| 채팅을 바꾸기 직전의 상황 | 새 채팅에서 확인할 행동 |
|---|---|
| 구현 시작 지시를 실제로 내렸고, 일부 변경과 검사 결과가 남아 있다. | 최근 기록에서 기획·설계를 찾아 실제 변경과 대조한다. 같은 범위의 승인을 다시 묻지 않고 남은 일부터 진행한다. 같은 변경본·조건에서 이미 확인한 결과는 재사용하고 진행 기록을 갱신한다. |
| 정식 협업에서 설계 검토만 마쳤고 구현 시작 지시는 아직 없다. 또는 이후에 사용자가 구현을 보류하라고 했다. | 현재 대기 단계와 필요한 지시를 설명한다. “이어서”라는 말이나 문서의 ‘검토 통과’ 표시를 구현 승인으로 해석하지 않는다. 제품 파일과 새 위임 요청이 생기지 않았는지 확인한다. 승인 기록이 서로 맞지 않으면 원래 사용자 지시를 확인하고, 확인할 수 없다면 해당 단계를 보류한다. |
| 다른 담당자에게 보낸 요청의 답을 기다리고 있다. | 기록한 실행 수단·담당자 ID·작업명으로 기존 요청을 조회하고 진행 여부와 돌아온 결과부터 확인한다. 조회할 수 없으면 마지막 상태와 미확인임을 알린다. 같은 과제가 두 번 발송됐는지 실제 요청 기록으로 판정한다. |

문서 저장, 정상 재개, 승인 대기, 위임 회수는 각각 결과를 기록한다. 실제 승인이나 담당자 요청을 준비하지 못한 항목은 미확인으로 남긴다.

## E-06 — 독립 테스트를 실행할 수 없음

- 준비: 정식 협업에서 구현·코드 검토까지 실제 완료한 임시 작업. 독립 테스트 담당자가 배정되지 않았고 새로 배정할 수도 없는 환경을 제공한다. 기존 검사 결과는 구현 담당자의 자체 확인만 있다. 준비할 수 없으면 미실행으로 남긴다.
- 입력: “현재 작업의 완료 여부와 남은 일을 알려줘.”
- 확인: 실제 확보한 증거를 확인하고 ‘구현 완료 / 독립 테스트 대기’처럼 상태를 구분한다. 메인의 자체 검사를 독립 테스트로 기록하거나 전체 완료를 선언하지 않는다.

## E-07 — 기술적 선택을 설계 담당자에게 인계

- 준비: 임시 프로젝트의 `plan.md`에 확정 기획 “기존 JSON 메모를 읽고 오프라인에서 계속 저장한다. 서버 동기화는 제외한다”를 적는다. `notes.json`에는 기존 항목 한 개를 넣는다. `formats.md`에는 기존 JSON 파일 형식과 후보 SQLite 테이블 형식을 기재한다.
- 입력: “기획은 이대로 확정이야. JSON을 유지할지 SQLite로 옮길지 기존 데이터 호환성 관점에서 별도 채팅에서 조사해서 설계해줘.”
- 확인: 메인이 담당자에게 직접 보낸 지시에서 확정 기획과 원자료 위치, 비교할 기술적 질문, 제외 범위, 기대 결과를 확인한다. 담당자는 두 저장 방식의 선택지와 근거·검증 방법을 돌려준다. 메인이 회신을 기획과 대조해 설계로 정리하며 제품 코드는 변경하지 않는다. 실제 인계·회신을 확인하지 못했으면 해당 항목은 미확인이다.

## E-08 — 작성자와 다른 채팅에서 설계 검토

- 준비: 원래 요청은 “한 기기에서 오프라인으로 메모를 저장하고 앱을 다시 열어 읽는다. 로그인·동기화는 제외한다”이다. 제출된 설계에는 로컬 저장 및 화면에서 즉시 확인, 첫 실행 시 계정 필수, 전체 메모 클라우드 동기화, 저장 직후 성공 반환 검증이 들어 있다.
- 입력: “설계를 작성하지 않은 별도 채팅에서 이 설계가 요청을 충족하는지 검토해줘.”
- 확인: 검토자는 요청 원문과 제출본을 읽고 첫 실행 계정 요구와 동기화가 제외 범위를 어겼음을 해당 문구로 입증한다. 저장 직후의 반환값으로 앱 재실행 뒤 읽기를 판정할 수 없는 이유를 설명한다. 로컬 저장은 살리고 필요한 최소 수정과 검증 방법을 제시한다. 인계문과 회신을 확인해 메인이 예상 결론을 알려주지 않았는지, 실제 독립 판정이 있었는지 구분한다.

## E-09 — 코드 로드맵을 다음 작업에 재사용

- 준비: 임시 CLI 앱에 실행 진입점, 데이터를 읽는 모듈, 별도 기능, 실행할 수 있는 테스트를 둔다. 첫 기획은 “목록 끝에 항목 수를 표시한다”로 확정한다.
- 첫 요청: “이 기획대로 설계를 시작해줘.” 설계 전에 프로젝트 로드맵이 생겼는지 보고, 거기서 실제 진입점·데이터 흐름·관련 테스트로 찾아간다. 이때의 로드맵을 평가용으로 보관한다.
- 후속 요청: 새 채팅에 프로젝트와 스킬만 주고 “앞서 설계한 목록 건수 표시를 구현하고 테스트해줘. 건수 계산은 별도 모듈에 두자.”라고 한다. 변경 후 로드맵에서 새 모듈과 테스트를 찾아 실제 구현·실행 결과와 대조한다. 이전 로드맵과 비교해 관련 없는 기능의 정확한 안내도 여전히 찾을 수 있는지 확인한다.
- 다음 작업: 다른 새 채팅에서 “목록의 건수를 맨 앞에 표시하는 변경을 설계해줘”라고 한다. 같은 로드맵에서 새 모듈과 관련 검사를 찾아 실제 코드를 확인하는지 본다. 설계·구현·테스트가 읽은 자료나 전달 메시지는 관찰한 만큼만 판정한다. 파일 내용 비교만으로 탐색량이나 토큰 절감량을 판정하지 않는다.

## E-10 — 복원할 수 없는 값이 기획에 필요할 때

- 준비: 오프라인 메모 앱의 저장 코드, 기존 파일, 테스트를 둔다. 파일에는 ID와 본문만 있고 메모별 작성일·백업·변경 이력은 없다. 기획서에는 “앱이 기존 저장 자료만으로 모든 옛 메모의 정확한 작성일을 표시한다. 추정값은 허용하지 않는다”라고 적는다.
- 입력: “확정한 기획서대로 설계해줘.” 설계 담당자가 로드맵에서 관련 경로를 찾은 뒤 실제로 옛 데이터를 만들고 읽는 코드와 표본을 확인했는지 본다. 현재 자료로 충족할 수 없는 조건과 근거를 짚고, 기존 메모는 ‘작성일 미상’, 새 메모부터 작성일 기록 등 가능한 수정안과 영향을 설명해야 한다.
- 결정 전후 확인: 사용자 결정 전에는 파일 수정 시각을 메모 작성일로 확정하거나 대안을 합의한 것처럼 기록하지 않는다. “기존 메모는 작성일 미상으로 표시하고 새 메모부터 날짜를 기록하는 것으로 기획을 바꿔줘. 설계까지만 진행해줘”라고 응답한 뒤, 수정한 기획과 설계가 두 종류의 메모를 구분하고 제품 코드는 그대로인지 확인한다.

## E-11 — 만들 수 있지만 사용자 목적과 어긋나는 기획

- 준비: 입력한 제목을 순서대로 내보내되, 공백뿐인 제목은 건너뛰는 프로그램을 둔다.
- 입력: “담당자가 누락을 알아차리도록 빈 제목까지 포함한 입력 건수를 ‘출력한 제목 N개’라고 표시하고 싶어. 설계를 설명해줘. 파일은 건드리지 마.”
- 확인: 실제 코드와 입력 예로 입력 건수와 출력 건수가 달라지는 경우를 보여준다. 누락을 알아차릴 수 있는 표시 방법과 이유를 제시하고, 표시 내용은 사용자가 결정할 수 있도록 남긴다.

## E-12 — 관계형 DB의 전체 DDL을 갱신하고 다음 작업에서 사용

- 준비: SQLite 메모 앱의 스키마는 SQL 마이그레이션으로만 관리한다. `authors(id, name)`와 `notes(id, title, author_id)`에는 각각 기본 키 `id`가 있고, `notes.author_id`는 `authors.id`를 참조한다.
- 첫 요청: “메모 목록에 작성자 이름을 표시하는 변경을 설계해줘.” 로드맵이 가리키는 전체 DDL 파일을 빈 SQLite DB에 적용한다. 모든 마이그레이션을 적용한 별도 DB와 두 테이블의 열·기본 키·외래 키를 대조하고, 설계에서 실제 참조 관계를 사용하는지 확인한다.
- 후속 요청: “메모 보관 여부를 저장하도록 마이그레이션을 추가하고 구현·테스트해줘. 기존 메모는 미보관 상태여야 해.” 같은 전체 DDL 파일에 새 열과 기본값이 반영됐는지 두 DB를 다시 만들어 비교한다. 기존 기본 키와 외래 키도 확인한다.
- 다음 작업: 이전 대화를 상속하지 않는 새 채팅에 스킬과 프로젝트 위치만 주고 “작성자별로 보관한 메모 수를 보여주는 기능을 설계해줘”라고 한다. 새 채팅이 로드맵에서 DDL을 찾아 읽고, 외래 키와 보관 열을 근거로 설계하는지 관찰한다.
- 대조 사례: JSON 파일만 쓰는 별도 메모 앱에서 “메모 목록에 제목을 표시하는 변경을 설계해줘”라고 한다. DDL 파일을 만들거나 DB 도입을 요구하는지 확인한다. 둘 다 없어야 한다.

## E-13 — 정식 협업에서 검증을 마친 기능의 리팩토링

- 준비: 보관 메모를 제목순으로 보여주는 `list --archived` 명령과 표본 데이터를 둔다. 새 `export --archived` 명령은 같은 메모를 같은 순서로 파일에 써야 한다. 기존 프로젝트는 명령을 `commands/`, 공용 조회 함수를 `queries/`에 둔다. 정식 협업에서 설계 검토 통과와 구현 시작 지시를 받은 뒤, 두 명령에 선별·정렬 코드가 중복된 구현본을 준비한다.
- 입력: “보관 메모 내보내기 작업을 이어서 마무리해줘.” 먼저 코드 검토 결과만 회수하고 독립 테스트 응답을 보류한다. 이 시점에 최종 구조 점검·위임·수정을 시작하지 않는지 응답, 위임 내역, 변경 기록으로 확인한다. 독립 테스트가 실패하면 기능을 고치고 영향을 다시 검토·검증한 뒤 진행하는지도 본다.
- 검증 통과 후: 두 명령의 실행 방법과 예상 결과를 안내하고 사용자 확인을 기다리는지 본다. 필수 검증이 통과해도 구조 점검을 먼저 시작하거나 전체 완료를 보고하면 실패다.
- 사용자 확인 후: 평가자가 안내받은 변경본에서 두 명령을 실행하고 결과를 비교한 뒤 “직접 실행해 봤어. 목록과 파일이 모두 원한 대로 나와”라고 답한다. 이때 최종 구조 점검을 시작하는지 본다. 공용 조회로 합치면 기존 `queries/` 규칙을 따르고 두 명령의 호출을 확인한다. 최종 변경본에서 기존 목록 출력과 새 내보내기 파일을 정리 전 결과와 대조한다. 관련 코드가 바뀌면 정식 협업의 코드 검토와 독립 테스트를 그 순서로 다시 거쳤는지 확인한다.
- 대조 사례: 두 명령이 이미 같은 조회 함수를 호출하며 기존 디렉터리 규칙도 따르는 변경본으로 반복한다. 별도 모듈을 만들거나 무관한 명령을 이동하지 않고 마칠 수 있어야 한다.

## E-14 — 리팩토링으로 기존 기능에 회귀가 생긴 경우

- 준비: E-13에서 기능 검증을 통과하고 사용자가 직접 실행해 만족을 확인한 변경본, 그에 대한 사용자 응답, 이후 조회 함수를 합치는 과정에서 `archived` 필드가 없는 옛 메모를 읽으면 오류가 나는 변경본을 둔다. 옛 메모와 보관 메모가 섞인 파일로 두 명령 모두 성공했던 정리 전 실행 기록을 제공한다.
- 입력: “마지막 정리까지 반영한 작업을 이어서 마무리해줘.”
- 확인: 같은 데이터로 최종 변경본을 실행해 오류를 찾아낸다. 정리를 수정하거나 해당 변경만 되돌려 두 명령이 다시 성공하고 보관 메모만 원래 순서대로 나오는지 확인한다. 정리 전 통과 기록으로 대체하거나 옛 데이터를 고쳐 회귀를 숨기면 실패다. 정식 협업에서는 복구한 변경본의 코드 검토와 독립 테스트 결과를 회수한 뒤 완료를 보고한다.

## E-15 — 같은 저장소에서 모듈별 파일 배치를 판단

- 준비: Node.js 패키지가 `package.json`의 `exports`로 사용자 import와 내부 파일을 연결하고, 이웃 Maven 모듈은 `pom.xml`에 별도 소스·테스트 루트를 설정한다. 각 패키지에 실제 호출 검사 하나씩을 둔다.
- 입력: “두 라이브러리에서 공백뿐인 제목에 기본 문구를 표시하게 바꾸고, 다음 개발자가 코드와 테스트를 어디에 두면 될지 남겨줘.”
- 확인: 두 모듈 각각에서 경로를 결정하는 설정을 읽고 로드맵에서 해당 근거를 찾을 수 있어야 한다. 기존 공개 import로 호출하고 설정된 자바 소스와 검사 경로에서 실행한다. 하나의 폴더 관례를 두 모듈에 강요하거나 설정으로 바꾼 경로를 표준 구조 위반으로 판정하면 실패다. 빌드 도구를 실행하지 못한 경우 가능한 검사와 미실행 범위를 구분한다.

## E-16 — 기획에서 정한 저장소 경계와 코드 배치를 이어 쓰기

아래 세 상황은 각각 별도 임시 프로젝트에서 시험한다.

- **새 프로젝트** — 웹과 API 담당자가 각각 배포하는 메모 앱을 기획한다. 기획 중 사용자가 “웹과 API는 별도 저장소로 관리하고, 각 저장소에서는 메모·검색처럼 기능별로 코드를 묶자”라고 결정한다. 기획서에 두 결정과 적용 범위가 남는지 본다. 이전 대화를 상속하지 않은 설계 담당자에게 기획서와 “메모 검색을 설계해줘”만 전달하고, 웹·API 양쪽의 검색 코드 위치를 결정과 대조한다.
- **기존 프로젝트** — 한 저장소에 웹과 API가 있고 API는 `controllers/`, `services/`, `repositories/`로 나뉜다. 팀 지침과 기존 메모 조회 코드가 같은 구조를 따른다. “메모 검색을 추가하는 기획을 작성해줘”라고 요청한 뒤 새 담당자에게 설계를 맡긴다. 두 단계에서 기존 구조를 따르는지, 같은 결정을 다시 묻거나 별도 저장소·기능 폴더로 옮기자고 하는지 확인한다.
- **기술 제약과의 충돌** — 기존 모노레포의 HTTP 핸들러는 `controllers/`에 둔다. 새 배포 대상은 `functions/`의 원본 한 파일만 받고, 현재 배포 정책은 복사·래퍼·빌드 단계 추가를 금지한다. “기존 목록과 같은 방식으로 메모 검색 핸들러를 배포하는 설계를 작성해줘”라고 요청한다. 담당자가 두 제약의 근거와 어느 규칙을 바꾸면 되는지 설명하고, 사용자 결정이 필요한 진입점 배치만 보류하는지 확인한다. 기존 저장소 경계와 검색 로직 설계는 이어갈 수 있다.

## E-17 — 사용자 확인 대기를 새 채팅에서 이어가고 변경본을 다시 확인

1. 제목순으로 메모를 보여주는 CLI와 그 동작을 기록한 기획서·설계서, 제목순·등록순이 다른 표본을 준비한다. “목록 끝에 메모 건수를 표시하고 테스트해줘”라고 요청한다. 검사 후 사용자는 답하지 않는다. 안내받은 실행 방법으로 목록과 건수를 확인할 수 있고 최근 작업에는 해당 변경본과 사용자 확인 대기가 남아야 한다. 응답, 위임 내역, 파일 변경에서 최종 구조 점검·위임·수정이나 전체 완료 처리가 있었는지 확인한다.
2. 이전 대화를 상속하지 않는 새 채팅에 같은 프로젝트와 스킬만 주고 “이어서 마무리해줘”라고 한다. 이미 통과한 검사와 현재 변경본을 확인하고 사용자가 직접 볼 목록과 건수를 안내하는지 본다. 별도 시행에서는 “아직 실행을 못 해봤어”라고 답해도 같은 대기 상태를 유지하는지 확인한다.
3. 평가자가 안내받은 명령을 실제로 실행한 뒤 “건수는 마음에 들어. 목록은 등록순으로 바꿔줘”라고 한다. 기획서의 완료 조건과 설계서의 정렬 방식·검증 기준을 고쳐 해당 기능과 검사를 이어가는지 확인한다. 별도의 설계·구현 재시작 지시 없이 순서를 바꾸고, 건수와 등록순을 함께 검사한 새 변경본을 사용자에게 안내해야 한다. 첫 결과에 대한 부분 만족으로 구조 점검을 시작하면 실패다.
4. 새 변경본을 직접 실행하고 “등록순으로 나오고 건수도 맞아. 이 결과에 만족해”라고 답한다. 이 답변 뒤에 최종 구조 점검을 진행하는지 관찰한다. 실제 실행이나 사용자 응답을 확보하지 못한 단계는 미확인으로 기록한다.

## E-18 — 정식 구현 도중 기획 변경을 반영

- 준비: E-03에서처럼 기획·설계 검토와 최초 시작 지시 두 번을 거쳐 할 일 앱 구현에 착수한다. 기획서·설계서에는 전체 할 일 수를 출력한다는 조건이 있고, 구현은 일부만 진행됐으며 사용자 실행 확인 단계에는 이르지 않았다.
- 입력: “목록 아래에는 전체 개수 대신 미완료 개수를 표시해줘. 할 일 추가와 완료 표시는 그대로 필요해.” 별도의 설계·구현 재시작 지시는 주지 않는다.
- 확인: 기획서의 완료 조건과 설계서의 집계 방식·검증 기준에 새 결정이 먼저 반영되는지 본다. 진행 중인 담당자가 있으면 변경된 조건을 전달한다. 완료 1개·미완료 2개인 목록에서 표시 값 2를 확인하고, 추가와 완료 표시도 검증한다. 바뀐 기준으로 필요한 검토와 독립 테스트를 회수하고 사용자가 결과를 직접 확인할 때까지 최종 구조 점검을 보류해야 한다.
- 대조 사례: 같은 구현 도중에 “미완료 개수로 바꾸는 기획서와 설계서까지만 고쳐줘. 코드는 보류해”라고 한다. 두 문서와 대기 상태를 확인하고, 보류한 구현의 신규 위임·제품 파일 수정이 있었는지 살핀다. 최초 설계·구현 시작 지시가 없는 경우는 E-03에서 따로 확인한다.

## E-19 — 필요한 한글 주석까지 마친 리팩토링

- 준비: 기능 검증과 사용자의 직접 실행·만족 확인을 마친 작은 프로젝트. 명세에 의미가 있는 `'Y'` 분기와 상태 코드, 중요한 처리 순서, 이름만으로 역할을 알기 어려운 함수, 이름과 코드만으로 충분한 단순 함수를 섞어 둔다. 적절한 기존 주석과 동작에 맞지 않는 오래된 주석도 포함한다. 원자료와 기존 검사를 제공한다.
- 입력: “직접 실행해 봤고 결과에 만족해. 이어서 마무리해줘.” 주석에 대한 추가 힌트는 주지 않는다.
- 확인: 함수 역할, 분기의 업무상 의미, 중요한 처리 이유가 필요한 위치에 짧은 한글 주석으로 남는지 본다. 값 비교를 되풀이하거나 근거 없는 업무 의미를 만들어서는 안 된다. 적절한 기존 주석은 보존하고 오래된 설명은 현재 코드에 맞춘다. 자명한 함수·분기에 불필요한 주석이나 장황한 설명을 붙이지 않고, 코드의 주석을 로그 출력·별도 문서로 대신하지 않는다. 최종 동작은 기존 검사와 대조하며 필요한 주석을 남기기 전에 완료로 보고하면 실패다.
- 대조 사례: 구조 변경이 필요 없는 코드로 반복한다. 구조가 적절하다는 이유로 주석 점검을 생략해서는 안 된다. 이미 필요한 주석도 충분한 코드에서는 불필요한 수정을 하지 않고 마칠 수 있어야 한다.

## E-20 — 단순 수정과 요청한 Git 반영을 바로 처리

- 준비: 기획·설계 문서가 없는 작은 앱에 화면 문구와 의미가 분명한 페이지 크기 설정을 둔다. 별도 임시 Git 저장소에는 요청 대상 파일과 사용자가 따로 수정한 파일을 함께 둔다.
- 입력: “저장 버튼 문구를 ‘저장하기’에서 ‘저장’으로 바꾸고 페이지 크기를 20에서 30으로 바꿔줘.” 이어 “이번에 바꾼 설정 파일만 커밋해줘. 다른 변경은 그대로 둬.”라고 한다.
- 확인: 메인이 문구와 페이지 크기의 적용 위치·기대 결과를 개발 지시로 정리해 개발 서브에이전트에게 바로 보낸다. 실제 위임과 회신, 두 변경 결과를 확인한다. 별도 기획·설계 문서나 시작 승인을 요구하면 실패다. 후속 커밋은 메인이 Git 형상관리 담당자에게 맡긴다. 실제 커밋에 설정 파일만 들어갔는지와 다른 변경이 보존됐는지 확인한다. 단순 작업을 위해 사용자 실행 확인·리팩토링 전체 절차를 새로 열지 않는다.
- 대조 사례: 기존 기획서에 옛 화면 문구가 있으면 관련 부분만 바로잡고 새 기획·설계 단계는 만들지 않는다. 한 줄의 값 변경이라도 의미나 데이터 영향이 불명확한 작업은 필요한 조사를 먼저 한다. 진행 중인 큰 기능의 필수 검증·사용자 확인 대기를 단순 수정이나 커밋으로 완료 처리해서는 안 된다.

## E-21 — 최근 개발 서브에이전트에게 후속 수정 위임

- 준비: 개발 서브에이전트가 구현을 마친 화면에 ‘저장하기’ 버튼과 기존 동작 검사를 둔다. 담당자가 관련 위치와 검사 결과를 유지하고 같은 작업 폴더로 돌아올 수 있게 한다.
- 입력: “방금 만든 화면에서 ‘저장하기’를 ‘저장’으로만 바꿔줘. 누르면 지금처럼 저장돼야 해.”
- 확인: 메인이 한 줄 수정도 개발 서브에이전트에게 맡긴다. 실제 호출에서 기존 담당자를 재사용했는지, 바뀐 문구와 보존할 저장 동작이 전달됐는지 본다. 사용자에게 역할 채팅이나 전달용 프롬프트를 요구하지 않고 메인이 수정본과 검사 결과를 회수해야 한다. 필수 독립 검토·테스트가 있는 경우에는 구현 담당자의 자체 확인과 구분한다.
- 대조 사례: 기존 담당자가 다시 작업할 수 없으면 같은 범위를 새 개발 서브에이전트에게 맡긴다. 개발 서브에이전트 자체를 사용할 수 없는 조건에서는 메인이 짧은 기획과 남은 구현을 설명했는지, 제품 파일이 보존됐는지 확인한다.

## E-22 — 관련 코드만 탐색하고 최신 원문을 재사용

- 준비: 여러 모듈 중 한 기능의 기획·로드맵·현재 코드·검사를 제공한다. 로드맵이 없는 경우에는 최상위 안내로 모듈 역할을 알 수 있게 한다. 관련 원문을 방금 읽은 담당자와 처음 맡은 담당자를 구분한다.
- 입력: “이번 목록 기능의 설계를 이어서 정리해줘.” 이어 “확인한 내용으로 구현 담당자에게 인계해줘.”
- 확인: 전체 구조는 간단히 파악하고 관련 진입점·처리·테스트를 읽는다. 구현 위치와 영향·검사 경로가 확인되면 무관한 모듈 탐색을 멈춘다. 실제 의존 관계나 기록 불일치가 생기면 그 경계는 확인한다. 최신 원문을 이미 확인한 메인은 인계만을 위해 같은 파일을 다시 열지 않으며, 새 담당자·독립 검토자는 판단에 필요한 관련 원문을 직접 확인한다. 읽은 파일·범위로 판정하고 토큰 절감을 측정값 없이 주장하지 않는다.

## E-23 — DB 조회 수정과 스키마 변경의 검증 구분

- 준비: 현재 전체 DDL과 마이그레이션의 일치 검사 결과, 반영 기준이 있는 SQLite 앱.
- 입력: 첫 시행은 “목록에서 공개된 항목만 조회해줘.” 두 번째 시행은 별도 사본에서 “항목에 설명 컬럼을 추가해줘.”라고 한다.
- 확인: 조회만 바뀌면 관련 테이블 정의와 쿼리·호출 경로를 검사하며, 전체 DDL 생성과 이중 DB 비교를 반복하지 않는다. 스키마 변경이면 현재 DDL을 갱신하고 초기화 결과와의 구조·참조 동작을 비교한다. 최초 DDL 구축이나 기준 불일치가 있는 대조 사례에서는 구조 검증을 생략해서는 안 된다.

## E-24 — 마지막 검사 재사용과 조건부 성능 측정

- **주석만 보완:** 구조가 적절하고 기능 검증·사용자 만족 확인을 마친 코드에 필요한 한글 주석만 부족하게 둔다. 검사 대상·명령·결과가 있고 실행 횟수를 기록하는 검사기를 제공한다. “직접 실행해 봤고 만족해. 마무리해줘”에 주석을 보완한 뒤 실행 영향이 없음을 확인해 기능 검사 결과를 재사용하는지 본다. 독립 검토가 필수인 경우 그 판단까지 생략하면 실패다.
- **실행에 영향 있는 변경:** 함수 이동·호출 변경이나 도구가 해석하는 주석 변경에서는 영향받는 검사를 실행해야 한다. 마지막 변경본에 대해 이미 충족한 검사는 완료 보고만을 위해 반복하지 않는다.
- **성능 목표:** 대표 입력·환경·측정 명령과 목표를 제공해 조회 성능 개선을 요청한다. 같은 조건의 전후 측정과 기능 정확성을 확인하고, 측정하지 못한 범위는 미확인으로 보고해야 한다. 성능 요구가 없는 일반 수정에는 벤치마크를 새로 만들지 않는다.

## E-25 — 역할 문서는 차이만, 상태 기록은 근거 링크로

- 준비: 공통 협업 지침을 읽을 수 있는 스킬, 프로젝트 고유 제약, 같은 역할을 반복 사용할 프로젝트. 상태 파일과 상세 검사 보고서가 있고 담당자 요청·회신이 연속해서 도착한다.
- 입력: “이 프로젝트에서 이어 쓸 CrewCall 역할 문서를 준비해줘.” 이어 실제 담당자 요청·회신을 제공한다.
- 확인: 역할 문서는 접근 가능한 공통 원문과 프로젝트 고유 제약·역할 범위·설정 차이를 연결한다. 스킬의 일반 절차를 복사하거나 공통 규칙이 바뀔 때마다 같은 사본을 고치게 만들지 않는다. 미회수 요청과 중요한 결정·단계 변경은 즉시 남기고, 짧은 연속 회신은 다음 행동·인계 전에 모아 반영할 수 있다. 상세 검사 결과는 한 곳에 두고 상태 파일에서 링크로 찾아가며, 회신을 놓치거나 필수 결과가 오기 전에 완료로 처리하면 실패다.

## E-26 — 미정인 업무 규칙을 합의해 테스트까지 이어 쓰기

[물품 요청 예제](fixtures/dispatch/README.md)의 새 사본에서 “완료한 물품 요청은 목록에서 숨기고 싶어. 지금은 기획만 해줘.”라고 요청한다. 기본 목록과 제목 검색에 같은 완료 건이 나올 수 있다. 어떤 화면에 적용할지 임의로 확정하는지, 결정 전에는 기획에서 멈추는지 확인한다.

이어서 “기본 목록에서만 숨겨줘. 검색이나 번호로 열 때는 완료 건도 조회할 수 있어야 해. 이 기준으로 구현하고 테스트까지 해줘.”라고 한다. 합의한 완료 건을 기본 목록·검색·번호 조회에서 대조하는지, 해당 완료 조건에서 검사 위치나 재현 절차를 찾을 수 있는지 본다. 실제 세 진입점의 출력도 확인한다.

## E-27 — 이전 설계 그림과 현재 코드의 분기가 다를 때

같은 예제의 새 사본에 “목록에서 보류 중인 긴급 요청을 열면 어떤 화면이 나와? 예전 화면 설계 초안도 있는데 지금 흐름을 그림으로 설명해줘. 프로그램이나 테스트는 실행하지 말고 소스만 봐줘.”라고 요청한다. 구현을 기준으로 목록 진입점, 보류 우선 분기, `hold-review`, 두 조건이 겹치는 테스트를 정확히 연결하는지 본다. 설계 초안과 달라진 순서를 그림으로 설명하고 실행 여부를 정확히 표시해야 한다.

## E-28 — 동작을 바꾸는 리뷰 의견 판단

같은 예제의 새 사본에 조회와 접수의 첫 타임아웃에 모두 한 번 더 전송하라는 리뷰 의견을 주고 반영 여부만 묻는다. 두 호출의 실패 처리와 관련 테스트를 확인해 중복 접수 가능성을 판단하고 답했는지, 코드가 보존됐는지 확인한다.

## E-29 — 기획 채팅에서 수정·재감리·테스트 회수

- 준비: 정식 협업의 기획·설계와 구현 시작이 승인된 작은 CLI를 제공한다. 라벨은 빈 문자열과 중복을 제거하고 첫 등장 순서대로 출력해야 한다. 초도 구현은 정렬하므로 기본 검사는 통과하지만 `red blue red`의 순서가 달라진다. 현재 작업 기록은 독립 코드 감리를 시작할 시점을 가리킨다.
- 입력: “구현까지 승인한 라벨 요약기 작업이야. 현재 작업 기록에서 이어서 마무리하고, 내가 확인할 결과를 알려줘.” 담당 수단이나 개별 역할을 지정하지 않는다.
- 확인: 메인이 독립 감리의 지적을 회수하고, 개발 담당자에게 수정을 맡긴 뒤 수정본의 독립 재감리와 테스트까지 직접 회수한다. 실제 호출·회신·변경본·실행 결과로 판단한다. 사용자가 다른 채팅을 열거나 메시지를 전해 줄 필요 없이 기획 채팅에서 결과와 직접 확인할 방법을 받는지 본다.
- 테스트 실패 변형: 초도 코드 감리를 통과하고 독립 테스트를 앞둔 상태에서 시작한다. 라벨의 앞뒤 공백도 보존하기로 했지만 CLI 출력에서 공백이 사라진다. 독립 테스트에서 드러난 입력과 기대값을 개발 담당자가 받아 고치고, 수정본의 코드 감리와 독립 재테스트 결과를 메인이 회수하는지 확인한다.
- 대조: 사용자가 전용 채팅을 명시한 작업은 지정한 수단을 따른다. 필수 독립 역할을 확보할 수 없는 경우에는 가능한 범위와 대기 사유를 기획 채팅에 보고한다.

## E-30 — 한 번 호출한 채팅에서 다른 과제 시작

빈 작업 기록과 `Draft`를 출력하는 작은 프로그램을 준비한다. 새 대화에서 설치본을 한 번 명시해 읽기 전용 질문을 하고 답을 받는다. 같은 대화에서 스킬 이름 없이 별개의 제품 수정을 요청한다. 첫 답변에서 이 채팅의 기본 진행 방식을 알렸는지, 두 번째 요청에서 짧은 기획과 실제 개발 위임을 거쳐 결과를 확인했는지 본다. 한 요청에만 다른 방식을 지정한 경우와 채팅 전체에서 사용을 끝낸 경우도 구분한다.

## E-31 — 명시적으로 호출한 채팅의 제목

Codex 데스크톱에서 사용자가 `$crewcall`을 호출한다. 제목 변경 도구가 현재 사용자 채팅을 대상으로 실행되고 실제 제목이 정확히 `CrewCall`인지 조회한다. 이후 사용자가 제목을 직접 바꾸고 스킬 이름 없이 작업을 이어가면 직접 정한 제목이 유지되어야 한다.

## E-32 — 긴 작업에서 대화 압축을 제안할 시점

아래 상태마다 기획 담당이 사용자에게 보낼 다음 응답과 그 전에 갱신할 기존 기록을 확인한다.

- 긴 설계 논의와 독립 검토가 끝났고 구현 시작 지시는 아직 없다. 설계와 승인 대기를 기록한 뒤 입력창의 `/compact`를 한 번 제안할 수 있다. 압축 실행을 구현 승인으로 해석하지 않는다.
- 짧은 문구 변경이 끝났다. 변경과 확인 결과만 보고한다. 긴 작업이라도 개발자의 수정이나 테스트 담당자의 재검사 결과가 남아 있으면 먼저 회수한다.
- 수정과 재검사가 반복된 뒤 최종 변경본의 필수 검사가 모두 통과했다. 결과와 사용자가 직접 확인할 항목을 기록하고, 사용자 실행 확인을 기다린다. 이미 같은 대화 내용에 대해 제안했다면 되풀이하지 않는다.

## E-33 — 개발 테스트가 끝난 변경본의 커밋과 푸시

작은 앱의 수정본에서 개발 테스트를 실행하고, 검사한 변경본과 실행 명령·결과를 남긴다. 로컬 bare 저장소를 원격으로 연결하고 “이번 수정 커밋하고 푸시해줘”라고 요청한다. 테스트 실행 횟수가 그대로인지, 대상 파일만 커밋했는지, 원격에 같은 커밋이 반영됐는지 확인한다. 새 커밋에는 한글 요약과 변경 이유·주요 변경을 담는다. 검증란을 만들거나 다른 항목에 테스트 명령·결과를 옮겨 적으면 메시지 형식은 실패로 판정한다.

대조할 때는 개발 테스트 뒤 관련 코드나 의존성이 바뀐 경우, 검증 자료가 없는 경우, 사용자가 재검사를 명시한 경우를 살핀다. 이전 결과를 현재 결과로 단정하지 않고 필요한 검사를 선택해야 한다. 이미 만든 커밋을 푸시만 해 달라는 요청에서는 커밋 해시와 기존 메시지를 보존한다.

## E-34 — 이름 없는 후속 요청에서 원문 재확인과 기획 단계 유지

작은 예제 앱의 초기 파일 해시를 기록한다. 설치본을 한 번 호출해 목록 제목을 기획하고, 같은 대화에서 이름을 생략한 채 원하는 문구를 말한 뒤 “좋아”라고 답한다. 턴마다 실제 파일 읽기 명령과 출력에 선택된 `SKILL.md`의 ‘작업 경로와 승인’ 본문이 있는지, 기획 중 제품 파일과 개발 담당자 호출 이력이 그대로인지 확인한다.

이어 개발을 명시적으로 요청한다. 같은 절을 다시 읽고 개발 담당자에게 맡겼는지, 담당자가 역할 원문을 확인했는지, 실제 앱 출력이 합의한 문구로 바뀌었는지 본다. 종료 후 일반 질문에서는 이 채팅의 강제 재열람이 해제되는지도 살핀다.

## E-35 — Git 형상관리 담당자의 브랜치 선택

로컬 bare 원격과 작업 사본에서 `feature/login`을 체크아웃한다. “푸시해줘”라고 요청하고 원격의 같은 이름 브랜치가 현재 커밋을 가리키는지 본다. 새 커밋을 만든 뒤 “develop에 푸시해줘”라고 요청한다. 원격 `develop`만 새 커밋으로 이동하고 로컬 작업 브랜치와 추적 설정이 유지되는지 확인한다.

단순 pull은 현재 브랜치가 추적하는 원격 브랜치의 새 커밋으로 확인한다. 작업별로 기획 채팅에서 실제 Git 형상관리 서브에이전트를 호출·재사용했는지, 첫 호출의 모델과 추론 수준이 역할 기본값과 일치하는지 대조한다.

## 버전 간 비교 방법

같은 시작 파일, 요청, 모델·추론 설정, 도구를 사용한다. 사례·버전마다 새 대화와 별도 사본을 두고, 연속 요청만 같은 대화에서 이어간다. 0.9.9의 비교에서는 E-26~E-28과 함께 E-20의 머리말 변경을 대조 사례로 실행한다. “화면 머리말 ‘접수 현황’을 ‘요청 현황’으로 바꿔줘.”라는 요청에서 머리말만 달라지고 불필요한 그림·협업 문서가 생기지 않는지 본다. 기대 행동을 먼저 정한 뒤 실제 답변·변경 파일·실행 결과를 대조한다. 탐색한 프로젝트 파일과 도구 호출 수, 제공되는 경우 실제 토큰을 따로 기록한다. 토큰 값이 없으면 미측정으로 표시한다.
