# CrewCall을 나에게 맞게 개선하기

CrewCall은 개인용 개발 스킬이다. 실제 작업에서 불편했던 행동을 확인하고 필요한 규칙을 조금씩 보완한다. 개인 선호는 사용자가 요청하거나 확인한 내용만 반영하며 추정해서 추가하지 않는다. 관리 문서인 이 파일은 다른 프로젝트에서 스킬을 실행할 때 읽을 필요가 없다.

## 사용 후 개선하는 순서

1. 어떤 요청에서 어떤 행동이 불편했는지 기록한다. 가능하면 요청 문구와 결과의 관련 부분만 남긴다.
2. 기대한 행동을 적고, 이번 작업에만 적용할 선택인지 앞으로 유지할 선호인지 구분한다.
3. 기존 지침에 이미 있는 규칙인지 확인한다. 규칙이 있는데 지켜지지 않았다면 문장을 추가하기 전에 발견하기 어려운 위치나 상충하는 표현부터 살핀다.
4. 관련 지침을 수정하고, 같은 상황과 인접한 정상 사례에서 판단이 맞는지 확인한다.
5. 실제로 확인한 결과와 남은 한계를 기록한다. 다른 업무에서도 쓸 근거가 없는 규칙은 공통 지침으로 확대하지 않는다.

## 기본 검사

현재 개발 PC에서 사용한 형식 검사 명령이다. 저장소 루트에서 실행한다. Python과 PyYAML 및 해당 skill-creator 파일이 있는 환경을 전제로 한다. 다른 PC에서는 설치된 검사기의 실제 위치를 확인한다.

```powershell
python -X utf8 'C:\Users\cslee1\.codex\skills\.system\skill-creator\scripts\quick_validate.py' '.\skills\crewcall'
```

이 명령은 스킬의 기본 형식을 검사한다. 참조 링크, UI 설정의 일관성, 사용자 요청을 제대로 수행하는지는 별도로 확인한다. 행동 평가는 [검증 사례](../evals/scenarios.md)를 사용하며, 모든 문서 변경 때 전체 사례를 반복할 필요는 없다.

최초 변환 당시의 대조 결과와 원본 위치는 [검증 기록](crewcall-0.9.1-verification.md)에서 확인한다.

## 피드백 기록 양식

개선 요청이 생기면 아래 항목으로 이 문서에 기록한다. 아직 제안인 내용과 실제 반영한 내용을 구분한다.

```text
날짜 / 작업 상황:
당시 요청:
관찰한 행동:
원하는 행동:
적용 범위: 이번 작업만 / 프로젝트 / 개인 스킬 공통
수정한 파일과 이유:
검증 사례 및 실제 결과:
상태: 제안 / 반영 / 검증 대기 / 확인 완료 / 보류
```

사용자가 스킬을 읽으며 이전 문서의 절 번호를 지워 달라고 요청했다. 실행 지침에는 현재 제목과 해당 주제 링크를 쓰고, 평가 사례와 완료 조건은 기존 식별자로 추적한다.

### 쉬운 문장으로 고친 뒤의 행동 시험

2026-11-20, CrewCall 0.9.1. 각 사례의 메인에게 이전 대화 없이 스킬 경로, 실습 폴더, 사용자 요청만 전달했다. 기대 답은 주지 않았다. 정식 협업의 후속 메시지는 평가자가 사용자 역할로 같은 메인에 보냈다. 역할 간 인계에는 독립 서브에이전트를 사용했다. 아래는 각 요청을 한 번씩 실행한 결과다.

| 요청 | 메인이 직접 한 일과 위임한 일 | 관찰한 근거와 판정 |
|---|---|---|
| **작은 수정** · 빈 이름이면 인사말만 반환하도록 수정하고 확인해줘 (E-02) | 메인이 직접 함수 한 개를 수정하고 호출했다. | **통과.** 파일 한 개만 바뀌었다. 평가자가 재호출해 빈 문자열은 `안녕하세요`, 민지는 `안녕하세요, 민지님`, 공백 한 칸은 기존 형식임을 확인했다. |
| **작은 설계** · 호칭을 ‘님’에서 ‘씨’로 바꾸려는데, 설계만 보여줘 | 별도 역할 없이 메인이 변경할 반환문과 두 입력의 기대값을 제시했다. | **통과.** 답변 전후 파일 해시가 같았다. 실제 파일의 반환문에는 여전히 ‘님’이 있었다. |

| **정식 협업** · 0 기반 위치로 목록의 할 일 하나만 완료 처리해줘 (E-03 변형) | 메인이 기획·설계를 직접 작성하고 각각 독립 검토를 받았다. 명시적인 구현 지시 후 구현 담당자, 코드 검토자, 독립 테스트 담당자에게 순서대로 맡겼다. | **통과.** 두 단계의 대기를 아래처럼 관찰했다. 구현 뒤에는 평가자도 새 목록 두 개로 위치 0과 1을 직접 확인했다. |
| **복구하기 어려운 변경** · 기존 메모 본문을 없애고 날짜별 건수만 같은 파일에 남겨줘 | ‘정식 협업’이라는 말 없이 요청했다. 메인이 변경의 영향을 판단해 기획과 독립 검토까지 진행하고 설계 시작 지시를 기다렸다. | **통과.** 1월 9일 2건·10일 1건이라는 집계 예를 보여줬고 원본 파일의 세 본문과 해시가 그대로였다. 이 사례는 첫 대기 지점에서 시험을 끝냈다. |

**정식 협업에서 관찰한 순서**

1. 기획 요청 뒤 메인이 세 완료 조건을 제시하고 독립 기획 검토 결과를 받았다. 이어 “좋아.”를 보냈더니 기획 확인으로 받아들이고 대기했다.
2. “설계를 시작해줘.” 뒤 메인이 `complete_task(items, index)`를 설계하고 독립 설계 검토를 받았다. “설계안 확인했어. 좋아.”에도 구현을 시작하지 않았다. 기획과 설계의 각 대기 지점에서 `tasks.py`의 SHA-256 앞 16자리는 시작 때와 같은 `cc4404bc3c28ebd4`였다.
3. “설계대로 구현을 시작해줘.” 뒤에 함수가 추가됐다. 코드 검토와 독립 테스트가 끝난 파일 해시는 `e282801721d2affe`로 바뀌었다. 위치 0 선택 결과는 `[True, False]`, 위치 1은 `[False, True]`였고 제목과 순서가 유지됐다.

병렬 실습 중 독립 역할 슬롯이 잠시 찼을 때 해당 메인은 검토를 기다렸다. 평가자는 슬롯이 비었다는 사실만 알려줬고 메인이 독립 검토 결과를 받은 뒤 다음 응답을 냈다. 실습은 공유할 수 있는 임시 폴더와 분리된 에이전트 대화에서 수행했다. 화면에 보이는 새 채팅의 개설, 전역 설치·자동 발견, 토큰 사용량은 이 시험의 확인 범위 밖이다. 시험에 사용한 스킬 파일 묶음의 SHA-256은 `2a9af331646c88987e612b74ef7a9b9b9233e89752586d14cb6710a4cd387719`이다(상대 경로 순으로 경로·NUL·파일 바이트·NUL을 연결).

### 단계별 파일을 읽어 새 채팅에서 재개한 시험

2026-11-20 · 0.9.1 · E-05의 대기·재개 사례. 첫 대화에 이름 표시 함수의 기획과 설계까지만 요청했다. 기획서와 설계서가 각각 파일로 남았고 최근 작업 기록에서 두 링크가 열렸다. 새 메인에게 이전 대화, 작업명, 문서 경로를 전달하지 않고 스킬과 제품 폴더만 알려줬다.

새 메인은 기록과 제품 코드를 대조해 ‘기획·설계 완료 / 구현 시작 지시 대기’를 찾아냈다. 이때 제품 파일 해시는 처음과 같았다. 이후 평가자가 “구현을 시작해줘”라고 하자 저장해 둔 설계로 구현하고 상태를 완료로 갱신했다. 평가자도 함수를 직접 호출해 빈 이름은 ‘손님’으로 바뀌고 일반 이름·앞뒤 공백·공백 한 칸은 보존되는 것을 확인했다. 두 대화는 이전 대화를 상속하지 않는 독립 서브에이전트에서 실행했다. 누락된 승인 근거 조회나 실행 중 위임의 재연결은 이번 실습에 포함하지 않았다.

### 코드 로드맵 재사용과 기획 수정 시험

2026-11-20 · 0.9.1. 실제 업무 자료 대신 작은 메모 앱과 제목 내보내기 프로그램을 사용했다. 각 실습의 메인에게 실행용 스킬, 대상 폴더, 사용자 요청을 줬다.

| 사례 | 관찰한 동작 |
|---|---|
| 코드 로드맵 재사용 (E-09 변형) | 제목 내보내기 함수를 추가한 담당자는 기존 로드맵에 `exporter.py`의 `plain_text`와 새 테스트 위치를 적었다. 기존 도움말 항목은 그대로였다. 평가자가 기존·신규 테스트 4개를 다시 실행해 모두 통과했다. 다음 설계를 맡은 새 대화는 파일명을 알려주지 않아도 같은 로드맵에서 함수와 테스트를 찾아 “출력된 제목 개수만 첫 줄에 표시”하는 조건을 설계했다. 그 전후 로드맵 파일의 해시는 같았다. |
| 옛 메모 작성일 복원 (E-10 변형) | 설계 담당자는 로드맵을 만들고 읽기 코드와 기존 메모 두 건을 확인했다. 파일 수정 시각으로 개별 메모의 정확한 작성일을 복원할 수 없다고 설명했다. ‘기존 메모는 작성일 미상, 새 메모부터 기록’을 추천하고 사용자에게 선택을 요청했다. 선택 전에는 기획·코드·데이터 세 파일의 해시가 처음과 같았다. |
| 목적과 어긋나는 표시 (E-11) | 별도 대화에서 빈 제목까지 ‘출력한 제목’으로 세자는 기획을 검토했다. 입력 세 건 중 두 제목만 출력되는 예를 코드에서 도출하고 ‘입력 3건 중 제목 2개 출력 · 빈 제목 1건 제외’를 제안했다. 담당자에게 누락 건수면 충분한지, 원본에서의 위치도 필요한지 사용자에게 물었다. |

### DB 구조를 기록하고 이어 쓰는 시험

2026-11-20 · 0.9.3 · E-12 변형. 각 실습의 메인에게 스킬과 임시 프로젝트의 위치, 기능 요청만 전달했다.

- **기존 SQLite 서가 앱**에서 책 소개 기능의 설계만 요청했다. 메인은 두 마이그레이션을 반영한 현재 DDL을 저장해 로드맵에서 연결했다. 평가자는 현재 DDL과 마이그레이션을 각각 빈 DB에 적용해 테이블·컬럼·기본 키·외래 키·인덱스가 같고 존재하지 않는 서가를 참조하는 도서는 양쪽 모두 거부함을 확인했다. 제안한 소개 컬럼은 설계서에만 있었다.
- **후속 구현**은 별도 대화에 맡겼다. 세 번째 마이그레이션과 기존 DDL 모두 `books.description`을 포함했고 앞선 두 마이그레이션의 해시는 유지됐다. 평가자가 두 DB를 다시 대조하고 기존 도서 한 권을 이전해 보니 제목·서가·외부 코드가 보존되고 소개는 NULL이었다. 실습 프로젝트의 테스트 2개도 다시 실행해 통과했다.
- **다음 설계**를 맡은 새 대화는 파일명을 알려주지 않아도 로드맵에서 최신 DDL을 열고 서가 외래 키와 소개 컬럼을 사용했다. “소개 없는 도서 수를 빈 서가까지 보여줘”라는 요청에 메모리 DB에서 집계를 실행해 소개 없는 책이 두 권인 서가, 모든 책에 소개가 있는 서가, 빈 서가에 각각 2·0·0을 반환했다.
- **빈 SQLite 프로젝트**에서 폴더별 메모 조회를 설계했다. 메인은 설계서에 구현 예정 SQL을 남겼다. 평가자가 그 SQL을 메모리 DB에 실행해 `notes.folder_id`가 `folders.id`를 참조하는 것을 확인했다. **DB 없는 제목 표시 함수**의 설계에서는 SQL 파일을 만들거나 DB 도입을 요청하지 않았다.
- **기존 전체 DDL이 있는 카드 앱**에서는 원래 경로인 `db/init.sql`에 선택적 라벨 외래 키를 추가했다. 로드맵에서 이 파일로 연결되며 SQL 파일은 하나였다. 평가자가 해당 DDL로 SQLite를 초기화해 라벨 생략, 등록된 라벨 연결, 없는 라벨 거부를 확인했다. 앱의 테스트 3개도 통과했다.

### 최종 리팩토링과 환경별 파일 배치 시험

2026-11-20 · 0.9.4. 격리된 프로젝트와 새 에이전트 대화에서 작업을 이어받게 했다. E-13·E-14는 메인 단독 경로의 변형으로 시험했다.

- **서로 다른 업무 규칙.** 화면에서는 대체 문구를 쓰고 내보낸 파일에서는 빈 줄을 보존하는 프로젝트에서는 별도 구현을 유지했다. 평가자도 공개 API 테스트를 실행하고 코드와 테스트 파일의 해시가 처음과 같음을 확인했다.
- **필수 검증 대기.** 납품 단말 확인을 사용자가 맡은 프로젝트에서는 로컬 테스트 2개가 통과했어도 메인이 구조 정리를 보류했다. 최근 작업에 대기 지점을 기록했고 제품 코드와 테스트의 해시는 유지됐다.

- **두 환경이 함께 있는 저장소(E-15).** 메인은 Java 모듈의 `pom.xml`에서 재정의한 `libsrc`·`checks`를, Node.js 모듈에서는 `package.json`의 공개 import와 테스트 스크립트를 찾아 공용 로드맵에 모듈별 근거를 남겼다. 평가자는 POM이 가리킨 소스를 JDK 8로 컴파일해 `demo.TitleCheck`를 실행하고 Node 공개 import를 쓰는 테스트 3개를 실행했다. 모두 통과했다. Maven 실행 파일은 없어 Maven 빌드 자체는 미실행이다.

정식 협업의 재검토·독립 테스트 순서는 지침과 평가 시나리오에서 대조했다. 그 전체 과정을 별도 역할로 재실행하거나 토큰 절감량을 측정하지는 않았다.

### 프로젝트 구조를 우선하는지 확인한 시험

2026-11-20 · 0.9.5 · E-16. 독립된 실습 폴더에서 새 프로젝트의 기획 인계, 기존 프로젝트의 설계, 배포 제약과의 충돌을 시험했다.

- **새 프로젝트 인계.** 첫 대화에서 웹과 API를 독립 저장소로 배포하고 각각 기능별로 구성한다는 결정을 기획서에 남겼다. 다음 대화에는 스킬과 폴더만 알려주고 앞선 기획의 설계를 요청했다. 설계자는 웹 검색 기능에 입력·결과 표시를, API 검색 기능에 요청 처리·조회를 배치했다. 두 저장소의 실제 소스가 없는 상태여서 세부 경로는 확인할 사항으로 남겼다.
- **기존 모노레포.** 현재 메모 목록의 검색을 요청한 뒤 다른 클라이언트도 기존 서버 API를 통해 검색해야 한다고 구체화했다. 메인은 README와 목록 코드를 따라 웹과 API를 한 저장소에 두고 `controllers → services → repositories`의 기존 경로를 이용하는 설계를 남겼다. 제품 구현은 요청 범위가 아니었다.
- **배포 제약과의 충돌.** 핸들러 위치를 정한 저장소 지침과 원본 파일 하나만 수집하는 배포 설정을 함께 제공했다. 메인은 기존 배치에서 배포할 파일이 없고 경로만 옮겨도 검색 모듈을 포함할 수 없다고 확인했다. 배포 규칙 변경과 프로젝트 구조 변경의 영향을 제시하고 결정 대기를 기록했다. 로컬 검색 동작은 확인했고 실제 배포는 수행하지 않았다.

### 사용자 실행 확인과 개발 중 기획 변경 시험

2026-11-20 · 0.9.6. 제목을 명령행에 입력해 출력하는 프로그램을 격리된 폴더에 두고, 평가자가 실제 실행 후 사용자 역할로 후속 답변을 보냈다.

- **만족을 확인한 뒤 구조 점검.** 평가자가 명령행에서 `B`, `(제목 없음)`, `A`를 확인한 뒤 그 결과에 만족한다고 답했다. 메인은 별도 시작 지시 없이 기존 표시 함수를 재사용해 중복을 제거했다. 평가자도 최종본의 출력과 테스트 2개를 다시 확인했다.
- **개발 중 변경과 실행 후 재변경.** 개발 중 “1부터 순번을 붙이자”는 요청에 메인이 기획·설계와 검증 기준을 먼저 고친 뒤 구현했다. 평가자가 번호가 붙은 결과를 실행하고 “순서는 좋지만 번호 대신 각 줄을 `- `로 시작해줘”라고 하자, 같은 문서를 갱신하고 구현·테스트를 이어갔다. 새 명령행 출력 세 줄과 테스트 2개를 확인했고 상태는 다시 사용자 실행 확인 대기였다.
- **정식 협업 중 변경(E-18 변형).** 최초 설계·구현 시작 지시를 받은 상태에서 제목을 ` / `로 이어 달라고 요청했다. 메인은 개정된 기획·설계에 대해 독립 검토를 받은 뒤 시작 지시를 다시 묻지 않고 구현했다. 코드 검토와 독립 테스트를 차례로 마쳤고, 평가자도 명령행에서 `B / (제목 없음) / A` 한 줄을 확인했다. 최근 작업 기록은 사용자 실행 확인 대기였다.
- **문서만 요청한 경우.** 개발 중 “가나다순으로 바꾸되 오늘은 기획서에만 적어줘”라고 했다. 기획서에는 정렬된 출력 예가 생겼고 설계·코드·테스트는 처음과 같았다.

### 리팩토링 한글 주석과 단순 작업 시험

2026-11-20 · 0.9.7. 사용자는 리팩토링의 끝에 필요한 한글 주석까지 포함하되 함수·분기·중요 코드의 의미를 짧게 설명해 달라고 요청했다. 이어 단순 문구·값 변경과 요청한 Git 반영은 별도 기획·설계 없이 처리하고, 메인과 최근 구현 담당자 중 효율적인 쪽을 판단해 달라고 했다.

주석의 상세 기준은 `refactoring.md`에 두고 SKILL.md와 완료 지침에서 연결했다. 단순 작업은 SKILL.md에서 바로 처리하도록 구분하고 기획·상태 기록·협업 지침의 문서 강제와 충돌하지 않게 맞췄다. 기존 기능의 필수 검증·사용자 확인 대기는 유지하며 담당자는 코드 재확인·인계·대기 비용을 비교해 고른다.

- **E-19 변형 실제 실행.** 이전 대화를 상속하지 않은 서브에이전트에 스킬 경로, 체험 목록 프로젝트 두 개와 사용자 만족 응답만 전달했다. 하나는 화면·내보내기가 이미 같은 변환 함수를 호출하고, 다른 하나는 같은 변환을 중복 구현했다. `'Y'`는 공개, `'P'`는 준비 상태, 예약 수량은 임시 점유라는 명세와 기존 검사를 제공했다. 메인이 먼저 두 예제의 출력 `체험 (준비 중): 3`, `(이름 없음): 0`, `일반: 6`과 내보내기 값을 직접 확인했다.

### 기획 채팅에서 수정과 재검토를 회수하는 시험

2026-11-23 · 0.9.10. 사용자가 기획 채팅에서만 대화하도록 역할 위임의 기본 수단을 서브에이전트로 정했다. 승인 범위의 수정 지시와 재검토·테스트 회수는 기획 담당이 맡는다. [E-29 입력과 판정 기준](../evals/scenarios.md#e-29--기획-채팅에서-수정재감리테스트-회수)

첫 시험에서는 독립 감리자가 첫 등장 순서 오류를 재현했지만, 이전의 “메인이 직접 처리” 문구를 읽은 기획 담당이 구현까지 수정했다. 재감리와 독립 테스트는 통과했으나 개발 위임 조건은 충족하지 못했다. 최종 지침에서는 개발 담당자가 없는 협업 작업은 메인이 후임을 정하고, 단독 작업에서 직접 수정할 수 있도록 구분했다.

- **감리에서 발견된 결함.** 설치본을 읽은 새 기획 담당에게 같은 초기 상태와 사용자 요청을 줬다. 감리자가 기본 검사에서 빠진 입력 `red blue red`를 찾아냈다. 메인은 개발 후임에게 수정을 맡기고 최초 감리자의 재검토를 받았다. 별도 테스트 담당자가 단위 검사 2건 및 함수·CLI 각각 5개 입력을 확인했다. 평가자도 최종 CLI의 출력을 대조했다. 메인이 이 과정을 기획 채팅에서 보고하고 사용자 실행 확인을 기다렸다.
- **독립 테스트에서 발견된 결함.** 다른 사본과 새 기획 담당으로, 초도 코드 감리를 통과한 상태부터 시작했다. 이 담당자는 저장소의 0.9.10 원본을 읽었다. 테스트 담당자가 `" red "`의 양끝 공백이 CLI에서 사라지는 실패를 재현했다. 개발 담당자가 수정하고 별도 감리자가 수정본을 확인한 뒤, 최초 테스트 담당자가 같은 변경본에서 완료 조건 3개와 자동 검사 3개의 통과를 확인했다. 메인은 공백을 눈으로 확인할 명령과 결과를 기획 채팅에 보고했다. 실습이 겹쳐 처음 테스트 담당자를 호출할 때 슬롯이 잠시 찼고, 평가자는 슬롯이 풀릴 예정임만 알렸다.

평가자는 두 최종 사본에서 단위 검사와 CLI 입력 세 가지씩을 다시 실행했다. 새 사용자용 역할 채팅 개설이나 사용자에 의한 메시지 전달은 두 실습 모두 없었다. 저장소 원본과 Codex 사용자 설치본의 11개 상대 경로와 파일별 SHA-256이 모두 일치했고, 스킬 형식 검사·버전 표기·문서 링크도 확인했다. 사용자가 전용 채팅을 지정하는 예외와 독립 역할을 끝내 확보할 수 없는 상황은 지침으로만 대조했다.

### 짧은 기획과 개발 위임 시험

2026-11-24 · 0.9.11. 예제 접수 앱과 새 기획 대화를 준비하고, 저장소의 스킬 경로와 사용자 요청을 전달했다. 평가자는 어느 역할에 맡길지나 기대하는 응답을 알려주지 않았다. 한 대화에서 세 차례 요청하고 실제 위임, 파일 상태, 목록과 이력의 출력을 확인했다. [작은 수정의 판정 기준](../evals/scenarios.md#e-02--작은-기능-수정) · [후속 수정의 판정 기준](../evals/scenarios.md#e-21--최근-개발-서브에이전트에게-후속-수정-위임)

| 사용자 요청 | 기획과 실제 결과 |
|---|---|
| “접수 목록 위에 ‘접수 현황’이라고 뜨는 거, ‘요청 현황’으로 바꿔줘.” | 기획 담당은 목록 제목만 바꾸고 목록·이력을 각각 실행해 제목과 접수 내역을 확인하겠다고 먼저 알렸다. 개발 서브에이전트에게 `display()`의 목록 분기, 두 조회 명령과 기대 출력을 전달했다. 개발 담당자가 제목 한 줄을 수정했고, 두 화면 모두 기존 접수번호와 상태를 표시했다. |
| “끝난 건들 좀 정리해줘.” | 기획 담당이 완료 건을 목록에서 숨기고 이력에 보관할지, 목록 아래에 모아 보여줄지 물었다. 답변 전에는 새 개발 지시가 없었고, 예제 파일 두 개의 SHA-256도 요청 전과 같았다. |
| “기본 목록에서만 완료 건을 숨겨줘. 접수 이력에는 그대로 보여야 해.” | 기획 담당은 기존 개발 서브에이전트에게 이어 맡겼다. 목록에는 접수 건 한 개만, 이력에는 접수 건과 완료 건 두 개가 모두 표시됐다. |

평가자도 두 조회 명령을 실행해 첫 수정본과 최종 결과를 각각 대조했다. 최종 함수는 빈 목록, 모두 완료된 목록, 상태가 섞인 목록의 두 화면에서 기대값과 일치했다. 예제에는 원래 파일 두 개만 남았다. 별도 기획서나 사용자용 역할 채팅을 만드는 단계는 없었다.

저장소 원본과 Codex 사용자 설치본의 11개 파일은 상대 경로와 SHA-256이 모두 일치했고, 두 사본 모두 스킬 형식 검사를 통과했다. 버전 표기, UI YAML, 문서 내부 링크와 변경분도 정적으로 검사했다. 개발 서브에이전트 배정이 끝내 불가능한 경우와 정식 협업의 단계 승인은 이번 행동 시험에서 재현하지 않았다.

### 채팅별 호출과 후속 작업 시험

2026-11-24 · 0.9.12. 사용자가 어느 프로젝트에서든 스킬을 한 번 명시적으로 부른 대화를 작업 단위로 삼는다. [E-30 검증 사례](../evals/scenarios.md#e-30--한-번-호출한-채팅에서-다른-과제-시작)

Codex 사용자 설치본을 가리키는 링크로 별도 에이전트 대화 두 개에서 시험했다.

- 첫 대화에는 스킬 링크만 보냈다. 기획 담당이 이 채팅에서 계속 CrewCall로 진행하겠다고 알리고 첫 요청을 기다렸다. 스킬 이름 없이 한 줄 수정의 담당자를 묻자 개발 서브에이전트에게 위임하는 흐름을 설명했다.
- 두 번째 대화에서는 기획 담당의 역할을 먼저 묻고 답을 받았다. 이어 이름 없이 예제 앱의 출력을 바꾸는 별개 작업을 요청했다. 같은 대화에서 개발 서브에이전트가 실제 수정을 맡았고, 평가자가 프로그램을 실행해 `Ready` 출력을 확인했다.

저장소와 사용자 설치본의 11개 상대 경로와 파일별 SHA-256이 일치했고 두 사본의 스킬 형식 검사를 통과했다. 사용자 데스크톱에서 직접 새 채팅을 여는 과정, 긴 대화의 자동 요약 이후 동작, 일회 예외와 종료는 이 시험에 포함하지 않았다.

### 호출한 채팅의 제목 확인

2026-11-24 · 0.9.13. Codex 데스크톱의 현재 사용자 채팅에서 `set_thread_title`에 제목 `CrewCall`만 전달했다. 반환된 채팅 ID를 대상으로 `read_thread`를 실행해 저장된 제목이 정확히 `CrewCall`임을 확인했다. 이번 실측은 현재 채팅의 제목 변경과 조회까지다. 새 채팅에서 설치본을 처음 호출하는 과정과 제목 도구가 없는 환경은 별도로 실행하지 않았다. [E-31 검증 사례](../evals/scenarios.md#e-31--명시적으로-호출한-채팅의-제목)

- 반복 작업이 확인되면 도구 스크립트가 필요한지 판단하기: 아직 구체적인 작업 없음.
