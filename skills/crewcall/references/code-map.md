# 코드 로드맵을 만들고 이어 쓰는 법

코드 로드맵은 **“이 기능을 이해하려면 어디부터 열어볼까?”**에 답하는 프로젝트 공용 문서다. 예를 들어 메모 저장을 맡은 사람은 저장 버튼의 처리 함수에서 파일 쓰기 함수까지 따라가고, 테스트 담당자는 같은 흐름을 검사하는 테스트를 찾을 수 있어야 한다.

## 처음 만들 때

메인은 기획을 마치고 설계에 들어갈 때, 설계안을 쓰거나 기술 조사를 위임하기 전에 대상 프로젝트의 로드맵을 준비한다. 정식 협업이면 사용자의 설계 시작 지시를 받은 뒤 진행한다. 기본 위치는 대상 프로젝트의 `docs/workflow/code-map.md`다. 같은 역할을 하는 구조 안내서가 이미 있다면 그 파일을 보완하고 최근 작업 기록에서 실제 위치를 연결한다.

1. **전체 구조는 얕게 파악한다.** 최상위 파일 목록과 프로젝트 안내서로 주요 앱·모듈의 역할을 한 줄씩 적는다. 빌드·패키지 설정, 진입점과 테스트 구성은 이번 작업의 관련 모듈부터 확인한다. 무관한 모듈의 소스, 자동 생성물과 외부 라이브러리는 구체적인 확인 이유가 있을 때만 연다.
2. **이번 기획의 흐름을 따라간다.** 관련 진입점에서 처리·저장·반환과 테스트까지 필요한 파일·함수를 확인한다. 실제 호출·의존 관계나 기록 불일치가 드러나면 그 경계까지 넓힌다. 완료 조건의 구현 위치와 영향·검사 경로가 확인되면 탐색을 마치고, 읽지 않은 영역은 개요로 남긴다.
3. **다음 사람이 직접 확인할 근거를 남긴다.** 경로는 프로젝트 기준으로 적고 주요 함수·설정 이름을 함께 쓴다. 경로와 이름이 실제로 존재하는지 확인한다. 코드가 아직 없거나 확인할 수 없는 연결은 그대로 표시한다. 새로 만들 예정인 코드는 해당 작업의 설계서에 적는다.

| 로드맵에서 찾을 것 | 기록 예시 또는 기준 |
|---|---|
| 구조와 진입점 | 기획에서 정한 구조 문서의 위치, 기능을 맡은 저장소·모듈과 개발 패턴, 시작 파일·함수, 다른 모듈이나 저장소와 연결되는 경계 |
| 새 파일을 둘 위치 | [개발 환경별 디렉터리 지침](project-layout.md)에 따라 관련 모듈의 소스·테스트 위치, 위치가 동작에 영향을 주는 경로와 근거 설정을 적는다. |
| 데이터가 오가는 길 | 입력 → 처리 → 저장 또는 외부 호출 → 결과. 형식이나 권한처럼 설계에 영향을 주는 제약은 근거 위치와 함께 적는다. |
| 관계형 DB를 쓰는 프로젝트 | [데이터베이스 DDL 지침](database-schema.md)에 따라 현재 구조를 담은 SQL 파일을 연결한다. 저장 기능별로 관련 테이블과 키를 가리킨다. |
| 테스트를 시작할 곳 | 어떤 동작을 어떤 테스트가 확인하는지, 실행 위치와 명령, 필요한 환경. 설정에서 읽은 명령과 직접 실행한 결과를 구분한다. |
| 확인한 범위와 기준 | 어느 작업 폴더·버전을 봤는지, 확인한 영역과 남은 질문. Git이면 기준 커밋과 관련 미커밋 변경, Git이 없으면 확인한 파일과 시점을 적는다. |

## 다음 설계·구현·테스트에서 읽는 순서

메인은 담당자에게 기획·설계의 해당 조건과 **로드맵의 관련 부분**을 함께 알려준다. 담당자는 필요한 진입점·코드·테스트를 확인하되 같은 맥락에서 최신 내용을 이미 확인했으면 변경된 부분만 읽는다. 새 담당자나 독립 검토자는 자신의 판단에 필요한 관련 원문을 직접 확인한다. 범위 확대와 종료는 위 기준을 따른다. 설계자는 구현 가능성을, 테스트 담당자는 로드맵의 검사가 이번 완료 조건을 확인하는지 대조한다.

기존 로드맵이 있으면 먼저 작업 폴더와 기준 버전을 대조한다. 그 뒤 달라진 파일, 추가·이동·삭제된 모듈과 이번 작업의 관련 경로부터 확인한다. 기준을 알 수 없거나 구조가 크게 바뀌었다면 최신 디렉터리·진입점·테스트 설정을 다시 훑고, 확인 가능한 설명은 살린다.

## 개발과 테스트를 마칠 때

구현 담당자는 바뀐 파일과 호출·저장 흐름을, 테스트 담당자는 새 검사 위치와 실제 실행 방법을 메인에게 돌려준다. 메인은 최종 변경본과 대조해 로드맵의 해당 항목만 고친다. 새 진입점은 추가하고 삭제된 파일이나 옛 명령은 제거한다. 이미 확인한 경로·이름은 그 근거를 재사용하고 추가 변경이나 불일치가 있는 부분만 다시 연다. 확인 기준을 갱신하고 영향이 없는 설명은 그대로 둔다. 달라진 항목이 없다면 최근 작업 기록에 그 결과만 남긴다. 다음 작업은 같은 로드맵에서 시작한다.

## 개발자가 코드 흐름을 물으면

질문한 기능의 로드맵이나 설계 그림을 현재 변경본과 대조한다. 진입점에서 결과를 결정하는 분기까지 짧게 따라가며, 개발자가 열어볼 파일·함수와 그 규칙을 검사하는 테스트를 연결한다. 해당 테스트가 없으면 그 사실과 확인 가능한 방법을 알려준다. 그림을 요청받았거나 여러 분기를 글로 설명하기 어려울 때는 현재 구현과 맞는 그림을 재사용하거나 관련 부분만 작은 Mermaid 흐름도로 보여준다.

소스에서 따라갈 수 있는 분기와 특정 입력에서 실제로 관찰한 경로를 구분한다. 실행 경로를 설명할 때는 어떤 입력과 로그·추적 기록 등으로 해당 분기를 확인했는지 짚는다. 테스트가 최종 결과만 확인했다면 관찰한 결과도 거기까지로 표시한다.
