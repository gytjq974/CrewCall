# 데이터베이스 구조를 SQL 파일로 기억하는 법

관계형 데이터베이스(DB)를 쓰거나 새로 도입할 프로젝트에서는 테이블을 만드는 SQL인 **DDL**을 대상 프로젝트에 남긴다. 메인은 코드 로드맵의 데이터 저장 항목에서 DDL의 실제 경로를 연결한다. 다음 채팅의 설계·구현·테스트 담당자도 여기서 관련 테이블을 찾아 읽는다. JSON 파일이나 비관계형 저장소만 쓰는 프로젝트에서는 그 저장 방식의 정의를 따른다.

## 기존 프로젝트를 처음 맡으면

DB를 사용하는 프로젝트의 로드맵을 만들거나, 로드맵 없이 DB 관련 개발을 바로 시작할 때는 먼저 DB 종류와 스키마 변경을 관리하는 원본을 확인한다. 원본은 프로젝트에 따라 SQL 파일, 마이그레이션(구조 변경 이력), ORM의 모델이나 스키마일 수 있다. 기존 DB만 있다면 접근이 허용된 환경에서 구조만 읽어 추출하고, 어느 환경을 확인했는지 기록한다.

- 현재 전체 구조를 담은 SQL 파일이 이미 있으면 반영 기준과 이후 스키마 변경 여부를 확인해 같은 경로를 쓴다. 변경 이력이나 모델만 있으면 프로젝트의 기존 생성 방법을 우선 사용해 **현재 구조를 한 번에 만들 수 있는 SQL 파일**을 한 번 남긴다. 정해진 위치가 없으면 `docs/workflow/schema.sql`을 쓴다. 로드맵에 DB 종류, 원본 위치와 어느 마이그레이션 또는 변경본까지 반영했는지 적는다. 모델과 DB가 다르면 확인한 차이와 적용 상태를 구분해 적는다.
- 프로젝트가 관리하는 테이블, 컬럼의 이름·자료형·NULL 허용 여부·기본값, 기본 키(PK)와 외래 키(FK)를 실제 DB 문법으로 기록한다. 예를 들어 메모가 폴더를 참조한다면 `FOREIGN KEY (folder_id) REFERENCES folders(id)`처럼 양쪽 컬럼을 표시한다. 복합 키의 컬럼 순서, 삭제·갱신 규칙, 고유 제약·인덱스 등 실제 정의도 보존한다.
- 이름이 `folder_id`여도 DB에 외래 키가 없을 수 있다. 코드로만 유지하는 관계는 로드맵에 근거와 함께 적는다. 자료가 부족하면 확인한 범위와 남은 부분을 표시한다. 파일에는 구조 정의만 담는다.

## 새 기능을 설계하고 개발할 때

설계자는 관련 테이블의 DDL을 쿼리·모델·저장 코드와 대조한 뒤 재사용할 키와 바꿀 컬럼을 정한다. 새 DB이거나 구조 변경을 제안하는 단계라면 작업 설계서에 제안 DDL을 SQL로 적고 **구현 예정**이라고 표시한다. 새 채팅에 넘길 때는 로드맵의 현행 DDL과 설계서의 변경안을 함께 가리킨다. 설계만 요청받은 동안에는 이 변경을 DB나 적용 대상 마이그레이션에 반영하지 않는다.

구현 담당자는 프로젝트가 쓰는 방식으로 구조를 변경한다. 마이그레이션을 쓰는 프로젝트에서는 이미 적용한 파일을 보존하고 후속 마이그레이션을 추가한다. 테이블·컬럼·키를 추가·수정·삭제하거나 이름을 바꾸면 **같은 작업에서** 현재 DDL도 갱신한다. 자동 생성 파일이라면 원본을 수정한 뒤 다시 생성한다. 쿼리나 모델만 바뀐 경우에는 현재 정의와의 호환성을 확인한다.

## 완료 전에 대조할 것

DDL 최초 구축·스키마 변경·원본과의 불일치가 있을 때는 가능하면 같은 종류의 임시 DB 두 곳을 각각 프로젝트 초기화 절차와 현재 DDL로 만들어 테이블·컬럼·키와 참조 동작을 비교한다. 기존 데이터를 이전하는 변경이면 이전 구조와 샘플 데이터에 후속 마이그레이션을 적용한 결과도 확인한다. 실행 환경이 없으면 원본과 DDL을 대조하고 실제 실행이 남았음을 기록한다.

스키마와 반영 기준이 그대로인 일반 조회·표시 수정은 관련 테이블 정의와 변경한 쿼리·호출 경로만 확인한다. 전체 DDL을 다시 생성하거나 위 DB 비교를 반복하지 않는다. 이전 검사 결과의 재사용은 [검증 기준](verification.md#어떤-검사를-다시-할지-정한다)을 따른다.

메인은 DDL과 로드맵의 링크·반영 기준을 확인한 뒤 결과를 최근 작업 기록에 남긴다. 이후 작업은 같은 경로를 다시 사용한다.
