# 다음 채팅에서 작업을 이어가는 법

여기서 **프로젝트**는 CrewCall을 사용해 개발 중인 앱이나 서비스다. **메인**은 사용자와 직접 이야기하고 각 담당자의 결과를 모으는 AI다. 메인은 작업을 어떻게 이어갈지에 따라 기록할 곳을 고른다.

| 언제 | 어디에 무엇을 남기나 |
|---|---|
| 설명만 요청받았다 | 채팅에서 답한다. “파일을 만들지 마”와 같은 사용자 지시도 우선한다. |
| 명확한 단순 개발을 맡긴다 | 기획 채팅에 변경 범위와 확인 기준을 짧게 정리하고, 개발 담당자의 변경·확인 결과를 보고한다. 기존 진행 기록이 있으면 관련 결과만 갱신한다. 단순 Git 반영도 기록을 위해 협업 문서를 새로 만들지 않는다. |
| 기능 개발 작업을 시작했다 | 메인은 시작할 때부터 `current.md`에 작업명과 현재 단계를 적는다. |
| 기획이 정해져 설계를 시작한다 | [코드 로드맵](code-map.md)을 확인하고 최근 작업 기록에 실제 위치를 연결한다. 새 담당자도 그 문서에서 관련 코드를 찾아간다. |
| 기획·설계를 별도 단계로 진행하거나 해당 문서를 요청받았다 | 해당 단계의 초안을 작업별 파일로 저장한다. 검토·결정 후 갱신하고 `current.md`에서 실제 파일을 연결한다. |
| 개발 중 기획이 바뀌었다 | 바뀐 요구와 기획·설계 문서, 새 검증 기준을 연결하고 구현 보류 여부와 사용자가 허용한 다음 행동을 적는다. |
| 구현과 필수 검증이 끝났다 | ‘사용자 실행 확인 대기’와 대상 변경본, 사용자가 직접 해 볼 방법을 적는다. 사용자가 그 결과에 만족했다고 답하면 대상과 응답 근거를 남기고 구조 점검으로 넘어간다. |
| 여러 작업에서 같은 역할 지침을 쓴다 | `roles.md`에 공통 지침의 원문 위치와 프로젝트별 역할 범위·추가 설정을 적는다. |
| 사용자가 “이 프로젝트에 CrewCall 문서를 준비해줘”라고 한다 | 메인은 프로젝트의 `AGENTS.md`, `roles.md`, `current.md`를 준비한다. 문서 준비만 요청받았다면 준비된 내용과 다음 행동까지 기록하고 마친다. |

먼저 프로젝트의 최상위 폴더에서 `AGENTS.md`를 확인하고, 역할과 진행 상황을 이미 기록하는 파일이 있는지 찾는다. 같은 용도의 파일이 있으면 그 파일을 그 자리에서 보완한다. 사용자가 적어 둔 지침, 이 프로젝트의 설정, 작업 중인 변경, 이전 승인과 채팅 ID를 보존한다.

## 기획서와 설계서

기획이나 설계를 실제 단계로 진행할 때는 같은 작업의 기존 문서를 갱신한다. 없으면 대상 프로젝트 안에 `docs/workflow/tasks/<작업명>/plan.md`와 `design.md`를 단계별로 만든다. 예를 들어 메모 복원 작업이라면 `tasks/memo-restore/`를 쓴다. 다른 작업은 다른 폴더에 둔다.

| 언제 저장하나 | 무엇을 적나 |
|---|---|
| 기획 초안을 검토에 보내거나 사용자에게 보여주기 전 | `plan.md`에 목표, 이번에 할 일과 제외할 일, 사용자 관점의 완료 조건, 결정할 사항을 적는다. 검토나 사용자 결정이 있으면 같은 파일에 반영한다. |
| 설계 초안을 검토에 보내거나 다음 담당자에게 넘기기 전 | `design.md`에서 해당 기획서를 연결하고, 선택한 방법과 이유, 바꿀 위치, 작업 순서, 완료 조건별 확인 방법을 적는다. |

기술 조사 결과 기획을 고쳐야 하면 원래 조건과 수정 제안을 구분하고, 최근 작업 파일에 결정이 필요한 질문과 근거를 연결한다. 새 채팅도 그 결정부터 이어간다. 문서에는 초안·검토 중·검토 통과 등 실제 상태를 적는다. 검토 통과, 사용자 결정, 다음 단계의 시작 지시는 구분한다. 기획만 했다면 설계 파일은 실제 설계를 시작할 때 만든다. 단순 개발은 채팅에 정리한 기획으로 인계하고, 기존 기획·설계와의 충돌은 [최소한으로 바로잡는다](planning.md#개발-중-기획이-바뀌면).

## `AGENTS.md` — 이 프로젝트에서 어느 지침을 읽을까?

프로젝트를 열었을 때 AI가 처음 참고할 안내다. 기존 파일에는 빠진 안내만 더한다. 새로 쓸 때는 프로젝트 이름과 확인한 실행·검증 방법을 적거나 README의 해당 부분으로 연결한다. 코드가 아직 없으면 지금 확인할 수 있는 정보만 적는다. 이번 작업으로 실행 방법이나 설정, 입력·출력이 달라지면 README에서도 해당 부분을 고친다.

아래는 기본 위치에 역할 문서와 상태 문서를 준비한 프로젝트의 예시다. 실제로 있는 문서만 연결하고, 프로젝트 최상위 폴더에서 링크가 열리는지 확인한다.

```markdown
## CrewCall 협업

- 일을 맡은 AI는 [역할 지침](docs/workflow/roles.md)에서 공통 지침과 자기 역할 부분을 읽는다.
- 이전 작업을 이어받은 메인은 [현재 상태](docs/workflow/current.md)에서 아직 답을 받아야 할 작업과 다음 행동을 확인한다.
```

## `roles.md` — 일을 맡은 AI는 무엇을 해야 할까?

기본 위치는 `docs/workflow/roles.md`다. 공통 규칙은 담당자가 접근할 수 있는 CrewCall 스킬 원문과 필요한 절을 연결한다. 프로젝트 자료에 접근할 수 없으면 인계 메시지에 필요한 부분만 전달할 수 있다. 단계 시작에 필요한 스킬 원문은 [시작·재개 지침](../SKILL.md#처음-시작하거나-이어받을-때)에 따라 직접 읽는다. `## 공통`과 실제로 맡길 역할 절에는 프로젝트에서 따로 정한 내용만 적는다.

- **공통**에는 작업 폴더, 프로젝트 규칙의 위치, 스킬 기본값과 다르게 정한 설정·제약을 적는다.
- **각 역할(메인 포함)**에는 프로젝트에서 맡은 영역, 수정할 수 있는 범위, 필요한 자료·결과 위치와 추가 조건을 적는다. 공통 책임은 [역할 협업 지침](collaboration.md)을 따른다.

모델이나 추론 수준은 이 프로젝트에서 따로 정한 값만 적는다. 나머지는 [역할별 기본 설정](collaboration.md#역할별-모델과-추론-수준)을 따른다. 원문 위치나 프로젝트 규칙이 바뀌면 관련 링크·설정만 갱신하고, 프로젝트의 결정과 진행 중인 작업의 승인 상태는 유지한다.

## `current.md` — 어디서부터 다시 시작할까?

기본 위치는 대상 프로젝트의 `docs/workflow/current.md`다. 새 메인은 스킬을 시작할 때 프로젝트 지침에 적힌 상태 파일 또는 이 기본 위치를 먼저 찾는다. 다른 위치의 기존 상태 파일을 쓰는 경우 프로젝트의 안내에서 찾을 수 있게 그 경로를 남긴다. 최근 작업 기록에서는 프로젝트 안에서 열리는 상대 링크로 기획서와 설계서를 가리킨다. 문서 확인과 전달은 [역할 인계 기준](collaboration.md#역할-인계)을 따른다.

작업을 보류하거나 다른 일로 전환하면 기존 작업명·단계·문서 링크·다음 행동은 남기고 현재 작업을 표시한다. 완료했으면 완료라고 적는다. 새 채팅은 기록이 가리키는 프로젝트·작업 폴더·브랜치와 실제 변경을 먼저 대조한다. 저장된 문서가 있다는 사실만으로 다음 단계가 승인됐다고 판단하지 않는다. 진행 중인 위임 결과를 확인할 수 없으면 그 상태를 남기고 중복 발송을 피한다.

이전 기록에 ‘테스트 통과 / 구조 점검 대기’라고만 적혀 있다면, 이번 실행 결과에 대한 사용자 응답을 확인한다. 만족 확인 근거를 찾을 수 없으면 실행 방법을 안내하고 ‘사용자 실행 확인 대기’에서 이어간다.

메인은 파일 맨 위에 아래 네 가지를 적는다. 새 프로젝트에서 아직 요청을 받지 않았다면 현재 단계는 ‘요구사항 대기’다. 이미 진행 중인 작업이라면 실제로 바뀐 파일과 담당자가 보낸 답을 보고 현재 단계를 적는다.

| 다음 메인이 궁금한 것 | 적을 내용 |
|---|---|
| 무엇을 어디에서 하고 있나? | 목표, 이번에 다룰 범위, 협업 방식, 현재 단계, 작업 폴더. 관련 Git 브랜치나 아직 커밋하지 않은 변경을 찾을 위치도 적는다. |
| 사용자가 무엇을 결정했나? | 확정한 범위와 남은 결정. 특정 단계의 시작 지시가 필요했다면 사용자가 직접 그 지시를 내린 메시지 위치를 적는다. |
| 무엇을 확인했나? | 완료 조건의 이름이나 번호, 결과 요약과 검사 근거 위치를 적는다. 조건별 상세 결과·검사한 변경본·실행 방법은 연결된 검사 결과 한 곳에 둔다. |
| 누구에게 무엇을 받아야 하나? | 담당 역할, 일을 맡긴 방식(별도 채팅 또는 서브에이전트), 그 채팅이나 에이전트의 실제 ID. 아직 답을 받지 못한 작업 이름과 마지막으로 확인한 상태, 다음 담당자가 할 행동 하나를 적는다. |

예를 들어 테스트를 맡기고 채팅을 바꾼다면 “테스트 중”보다 “앱을 다시 열어도 메모가 남는지 테스트 담당자에게 확인 요청함. 다음 메인은 그 담당자의 결과를 확인할 것”이 유용하다. 여기에 실제 담당자 ID와 검사 대상 변경분을 함께 남기면 같은 테스트를 중복해서 맡기는 일을 피할 수 있다.

단계 변경, 중요한 결정, 새로 맡긴 미회수 요청은 즉시 기록한다. 단계나 결정을 바꾸지 않는 짧은 연속 답변은 다음 행동·인계 전에 모아 반영할 수 있다. 필요한 결과를 모두 받았는지 대조해 요청 누락이나 성급한 완료 처리를 막고, 지난 결정과 상세 검사 근거는 원문 위치로 연결한다. 이어받은 메인은 아직 답을 못 받은 작업의 실제 상태부터 확인한다. 기록과 파일 내용 또는 사용자 지시가 다르면 [시작·재개 지침](../SKILL.md#처음-시작하거나-이어받을-때)에 따라 원래 근거를 확인한다.
