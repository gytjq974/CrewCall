# 수정 전후를 비교하고 완료한다

메인은 “사용자가 해달라고 한 일이 실제로 되는가?”를 확인한다. 사용자와 정한 최신 완료 조건을 기준으로 삼고, 정식 협업에서는 그 조건이 반영되어 검토를 통과한 설계를 사용한다.

## 사용자가 하는 방법으로 확인한다

“저장한 메모가 다음 실행에도 남는다”가 조건이라면 일반 사용자로 앱을 열어 글을 쓰고 저장한다. 앱을 완전히 종료한 뒤 다시 열어 같은 글이 보이는지 확인한다. 관리자 권한으로 저장 함수만 호출했다면 확인한 범위는 그 함수의 동작까지다. 모의 환경에서 얻은 결과와 실제 사용자 경로에서 관찰한 결과도 구분한다.

기획에서 결과가 갈리는 예시를 합의했다면 같은 입력과 기대 결과를 검사한다. 해당 완료 조건에서 기존 테스트의 파일·테스트 이름이나 직접 확인한 절차를 찾을 수 있게 연결하고, 빠진 사례만 보완한다.

버그를 고쳤다면 같은 화면이나 호출 방법, 권한, 입력값, 판정 기준으로 **수정 전과 후**를 비교한다. 메모의 경우 “다시 열면 글이 비어 있었다 → 같은 과정을 거치니 입력한 글이 보였다”처럼 실제로 본 두 결과를 함께 적는다. 수정 전 상태를 확인할 수 없었다면 그 이유와 수정 후에 직접 확인한 범위를 적는다.

## 어떤 검사를 다시 할지 정한다

먼저 이전 검사 결과와 이후 변경분을 대조한다. 관련 코드, 입력, 권한, 실행 환경, 판정 기준이 같다면 그 결과를 사용할 수 있다. 최종 변경본이 이 조건을 만족하는 검사로 이미 확인됐다면 같은 검사를 반복 실행하지 않는다. 같은 커밋이라도 작업 폴더에 아직 커밋하지 않은 수정이 생겼다면, 그 수정의 영향을 받는 검사만 다시 한다. 여러 변경이 합쳐져야 작동하는 기능은 합친 상태에서 확인한다.

일반 한글 주석만 바뀌었다면 변경분에서 실행 영향이 없음을 확인하고 기존 기능 검사 결과를 재사용한다. 도구 지시·코드 생성 등 동작에 영향을 주는 주석은 이 예외에 포함하지 않고 해당 영향을 검증한다.

독립 테스트 담당자는 사용자 요청·결정 또는 승인된 설계에 적힌 조건을 직접 읽고, 실제 결과와 대조해 기존 검사 결과의 재사용 여부도 판단한다. 결과 재사용으로 필수 검토나 담당자의 독립 판단을 생략하지 않는다. 별도 실행이 요구되거나 기존 자료로 판단할 수 없으면 직접 실행한다. 검사 결과를 다른 담당자에게 전달할 때는 대상 변경본과 실행 조건, 검사 방법, 실제 결과를 함께 적는다. [역할 인계](collaboration.md#역할-인계)

프로젝트 지침이나 사용자가 전체 검사를 요구하거나, 일부만 검사해서는 영향을 받은 기능을 확인할 수 없는 구체적인 이유가 있을 때는 기존 기능 전반을 검사한다.

## Git 반영과 커밋 메시지

Git 형상관리 담당자는 작업 전 현재 브랜치·HEAD·작업 폴더 상태를 확인하고, 요청한 작업의 파일·커밋·원격·브랜치가 실제 대상과 맞는지 대조한다.

- **Pull**은 현재 브랜치의 추적 대상을 확인해 실행한다. 추적 대상이 없거나 요청과 다르면 그 상태를 메인에게 보고한다. 충돌 해결에 제품 파일 수정이 필요하면 위치를 메인에게 전달한다.
- **Push**는 현재 작업 브랜치의 `HEAD`를 보낸다. 사용자나 저장소 지침이 지정한 원격을 확인하고, 대상 브랜치 지정이 없으면 현재 브랜치와 같은 이름을 사용한다. 로컬 브랜치 및 대상 ref의 유효성, 원격 주소와 반영 범위를 확인한 후 `git push <원격> HEAD:refs/heads/<대상>`으로 보낸다. 현재 브랜치에서 실행하며 체크아웃이나 추적 설정 변경은 하지 않는다. 일반 푸시가 거절되면 원인과 대상을 메인에게 보고한다.

커밋·푸시 전에 대화에서 공유된 검증 결과, 테스트 기록 또는 CI 기록과 Git의 변경분을 대조해 개발 중 통과한 검사가 이번 반영본에도 유효한지 간단히 판단한다. 커밋할 때는 스테이징된 변경분을, 푸시할 때는 실제로 보낼 커밋을 기준으로 본다. 기존 근거가 유효하고 필요한 검증을 모두 마쳤다면 대상 파일·커밋·브랜치 등 Git 반영 범위만 확인한다. 변경의 영향을 받은 검사와 근거가 없거나 아직 실행하지 않은 필수 검사만 실행한다. 사용자가 재실행을 명시했거나 저장소에서 훅·CI 등 검사를 요구하면 그 조건을 따르고 우회하지 않는다.

이미 커밋된 변경의 푸시만 요청받았으면 기존 커밋을 그대로 보낸다. 아래 메시지 형식을 맞추기 위해 `amend`하거나 커밋 이력을 다시 쓰지 않는다.

새 커밋을 만들 때는 사용자 지시와 저장소 규약을 우선한다. 별도 형식이 없으면 Conventional Commits의 `유형(범위): 한글 요약` 형식을 쓴다. 범위는 선택이며, `feat`, `fix`, `docs`, `refactor`, `test`, `chore` 등 변경 목적에 맞는 유형을 고른다. 제목 뒤에 빈 줄을 두고 본문은 다음 순서로 짧게 적는다.

- **변경 이유**에는 해결하려는 문제나 변경 목적을 쓴다.
- **주요 변경**에는 사용자가 경험하는 동작이나 유지보수자가 알아야 할 변경을 쓴다.

기본 커밋 메시지에는 검증 명령·결과, 기존 결과를 재사용한 근거, 미검증 범위를 넣지 않는다. 검증 근거는 작업 결과를 보고하고 프로젝트의 기존 검증 기록을 갱신할 때 남긴다.

`BREAKING CHANGE`나 이슈 참조는 해당할 때만 덧붙인다. 프로젝트마다 별도 커밋 템플릿 파일을 만들 필요는 없다.

```text
fix(메모): 제목이 없는 메모를 목록에 표시

변경 이유
- 제목을 비워 저장한 메모를 목록에서 다시 열 수 없었다.

주요 변경
- 제목이 없는 메모를 목록에 ‘제목 없음’으로 표시해 다시 열 수 있게 한다.
```

## 성능이 완료 조건에 포함된 경우

성능이 이번 완료 조건에 포함됐을 때만, 합의한 지표와 대표 입력·부하, 실행 환경, 측정 방법을 맞춰 수정 전후를 비교하고 기능 정확성도 유지되는지 확인한다. 실제 측정값 없이 성능이 개선됐다고 단정하지 않는다. 성능 목표가 없는 일반 작업에 벤치마크를 요구하지 않는다.

## 사용자가 직접 실행해 결과를 확인한다

이 절은 기능 개발의 결과를 확인하는 단계다. [단순 문구·값 수정이나 Git 반영](../SKILL.md#작업-경로와-승인)만 요청받았으면 필요한 확인과 결과 보고로 마친다. 기존 기능 개발에서 아직 남은 필수 검증이나 사용자 확인을 단순 수정·Git 반영으로 대체하지는 않는다.

기능과 필수 검증이 통과하면 메인은 사용자가 **이번 변경본**을 직접 해 볼 수 있게 작업 폴더, 실행 명령이나 화면 경로, 대표 입력과 기대 결과를 알려준다. 예를 들어 “빈 제목으로 저장한 뒤 목록을 다시 열어 보세요. ‘제목 없음’으로 보입니다. 실행해 보시고 원하는 결과인지, 바꾸고 싶은 점이 있는지 알려주세요”라고 안내한다.

최근 작업 기록에 확인할 변경본과 실행 방법을 남기고 **‘사용자 실행 확인 대기’**로 둔다. 이때는 최종 구조 점검도, 그 점검의 위임도 보류한다. 테스트 성공이나 응답이 없는 상태만으로 단계를 넘기지 않는다. 새 채팅에서 “이어서 해줘”라고 해도 같은 확인을 기다린다.

- **현재 결과에 만족한다.** “직접 실행해 보니 원하는 대로야”처럼 대상과 만족 여부가 분명하면 그 결정을 기록하고 [최종 리팩토링](refactoring.md)을 시작한다. 리팩토링 시작 문구를 따로 받을 필요는 없다.
- **바꿀 점이 있다.** 요구가 바뀌면 [개발 중 기획 변경 절차](planning.md#개발-중-기획이-바뀌면)를 따른다. 이미 합의한 동작이 실패한 경우에는 승인된 범위에서 결함을 고친다. 수정본에서 영향을 받는 검증을 다시 마치면 사용자에게 실행 확인을 요청한다.

## 정식 협업의 순서와 완료 보고

정식 협업은 필요한 시작 지시와 앞 단계의 필수 검토 통과를 확인한 뒤 **구현 → 코드 검토 → 독립 테스트** 순서로 진행한다. 검토자는 수정한 코드에서 오류, 이전에 되던 기능이 깨진 곳, 합의한 범위를 벗어난 곳을 찾는다. ‘수정 요청’이면 현재 단계에서 보완하고 지적 사항과 수정의 영향을 다시 검토한다. ‘사용자 결정 필요’이면 해당 결정을 기다린다. [작업 경로와 승인](../SKILL.md#작업-경로와-승인)

사용자 실행 확인을 거쳐 구조와 [필요한 한글 주석](refactoring.md#코드에-남길-짧은-한글-주석)까지 점검한 뒤, 정식 협업에서 리팩토링으로 제품 코드를 고쳤으면 해당 변경분의 코드 검토와 영향을 받는 독립 테스트를 순서대로 마치되 [검사 재사용 기준](#어떤-검사를-다시-할지-정한다)을 적용한다. 최종 변경본을 기준으로 다음 작업자가 찾아갈 경로와 검사 방법을 로드맵에 반영한다. [코드 로드맵 갱신 방법](code-map.md#개발과-테스트를-마칠-때)

관계형 DB의 구조가 바뀌면 현재 DDL에 테이블·컬럼·관계가 실제 변경대로 반영됐는지 확인한다. [DB 구조 대조 방법](database-schema.md#완료-전에-대조할-것)

메인은 처음 요청과 비교해 무엇이 됐는지, 어떻게 확인했는지 보고한다. 수정한 파일은 구분·파일·변경 내용이 있는 표에 적는다. 필수 조건이 실패했거나 확인할 수 없었다면 그 조건과 이유를 밝힌다. 필수 검토나 테스트가 남았다면 “구현 완료 / 독립 테스트 대기”처럼 끝난 단계와 남은 단계를 함께 적는다. 필수 조건과 발견한 위험을 모두 확인하면 마친다.
