# 사용자가 실행 결과에 만족한 뒤 코드를 정리하는 법

리팩토링은 호출자와 사용자가 보는 동작을 유지하면서 다음 사람이 코드를 이해하고 수정하기 쉽게 만드는 일이다. [Martin Fowler의 리팩토링 정의와 원칙](https://refactoring.com/)

구조 점검은 **필수 검증을 모두 통과하고 사용자가 그 결과를 직접 실행해 만족한다고 확인한 뒤** 메인이 시작한다. 정식 협업의 코드 검토와 독립 테스트도 먼저 마친다. 대기 중이거나 변경 요청이 들어오면 [사용자 실행 확인 절차](verification.md#사용자가-직접-실행해-결과를-확인한다)를 따른다.

## 이번 변경에서 살필 세 가지

코드 로드맵과 변경 내역이 가리키는 관련 모듈의 코드·호출부·테스트부터 읽는다. 실제 호출·의존 관계나 중복된 업무 규칙의 근거가 있을 때만 범위를 넓히고, 동작·변경 영향·파일 배치를 판단할 근거를 확보하면 추가 탐색을 멈춘다. 파일 위치는 [대상 모듈의 개발 환경에서 확인한 규칙](project-layout.md)을 기준으로 판단한다.

| 확인할 질문 | 판단과 조치 |
|---|---|
| **다음에 이 규칙을 바꾸면 몇 곳을 고쳐야 하나?** | 두 곳이 같은 업무 규칙을 구현하는지 입력·출력·예외 처리로 확인한다. 같으면 기존 함수나 모듈을 먼저 재사용한다. 비슷해 보여도 요구가 달라 따로 바뀌거나, 합치면 호출자마다 분기 옵션을 넣어야 한다면 분리한 이유를 남긴다. [Sandi Metz의 중복과 추상화 사례](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction) |
| **함수 하나가 맡은 일을 이름으로 설명할 수 있나?** | 계산과 파일 저장처럼 함께 읽기 어려운 일이 섞였다면 하나를 이름 있는 함수로 추출한다. 반대로 한 줄을 알기 위해 여러 파일의 전달 함수만 따라간다면 불필요한 내부 함수를 호출부에 합친다. [함수 추출](https://refactoring.com/catalog/extractFunction.html) · [함수 인라인](https://refactoring.com/catalog/inlineFunction.html) |
| **다른 개발자가 이 파일을 어디서 찾을까?** | 대상 프로젝트의 디렉터리 규칙과 이웃 기능의 실제 배치를 확인한다. 책임이 잘못 놓인 함수나 파일은 그 기능을 소유한 기존 모듈로 옮기고 호출부·테스트·로드맵 경로를 맞춘다. 공개 import 경로, 실행 진입점과 모듈 간 의존 방향도 확인한다. [함수 이동](https://refactoring.com/catalog/moveFunction.html) · [Google의 코드 검토 기준](https://google.github.io/eng-practices/review/reviewer/looking-for.html) |

예를 들어 화면과 내보내기가 모두 빈 제목을 ‘제목 없음’으로 보여준다면 한 표시 함수를 쓴다. 반면 교환용 파일에서 빈 제목을 빈 칸으로 보존해야 한다면 두 동작은 따로 둔다. 다음 사람이 펼쳐 볼 파일이나 함께 고칠 곳이 실제로 줄어드는지가 판단 기준이다.

중복을 합칠 때도 기획에서 정한 저장소·모듈 경계와 의존 방향을 지킨다. 독립 배포하는 두 앱이 서로의 내부 코드를 가져와야만 합칠 수 있다면 현재 구조를 유지한다. 공용 패키지 도입처럼 경계를 바꾸는 선택은 이점과 배포 영향을 설명해 별도로 결정한다.

## 코드에 남길 짧은 한글 주석

이번에 개발·정리한 코드에는 사람이 이해하는 데 필요한 설명을 **코드 가까이에 짧은 한글 주석**으로 남긴다. 함수의 역할, 분기의 업무상 의미, 중요한 처리의 이유 중 이름과 코드만으로 드러나지 않는 내용을 설명한다.

- **함수:** 역할을 짧게 설명한다. 이름만으로 충분하면 생략하고, 함수마다 긴 설명이나 정형화된 문서 블록을 붙이지 않는다.
- **분기:** `if`·`else`·`switch` 등을 살펴 조건값의 의미나 경로를 나눈 이유가 불명확한 곳에 설명을 붙인다. 조건식을 그대로 읽어 주거나 자명한 분기마다 주석을 달지는 않는다.
- **중요 코드:** 처리 순서, 예외 처리, 호환성 유지처럼 코드를 읽어도 알기 어려운 이유를 한두 줄로 남긴다. 의미는 기획·설계·호출부·테스트에서 확인하고 추측해 적지 않는다.

예를 들어 명세에서 `useYn`의 `'Y'`가 기능 사용 가능을 뜻한다면 다음처럼 쓴다. “값이 Y인지 확인”처럼 식을 반복하지 않는다.

```js
if (useYn === 'Y') { // 기능 사용 가능
  enableFeature();
}
```

기존 주석도 최종 코드와 맞추고 중복되거나 불필요하게 긴 설명은 정리한다. **구조를 바꿀 필요가 없더라도 이 점검을 거치며, 필요한 주석 작성·정리까지 마쳐야 리팩토링이 끝난다.** 이미 충분히 설명된 곳에 주석을 더 붙일 필요는 없다.

## 정리하고 다시 확인하는 순서

1. **동작 기준을 확보한다.** 통과한 변경본과 검사 결과를 확인한다. 기존 동작이 테스트에 빠져 있으면 손대기 전에 관련 공개 함수나 실제 진입점에서 대표 입력·경계값을 실행해 기대 결과를 확보한다.
2. **근거 있는 부분만 고친다.** 중복 규칙 한 곳 통합, 함수 하나 이동처럼 확인할 수 있는 크기로 나눠 실제로 수정하고, [검사 재사용 기준](verification.md#어떤-검사를-다시-할지-정한다)에 따라 각 변경의 영향을 확인한다. 구조가 이미 알맞으면 그대로 둔 이유를 확인하고 주석 점검으로 넘어간다. 공개 동작이나 저장 형식 변경, 이번 기능 밖의 광범위한 재배치는 별도 작업으로 제시한다.
3. **필요한 한글 주석을 마무리한다.** 위 기준으로 함수·분기·중요 코드의 설명을 보완하고 최종 동작과 대조한다.
4. **최종 변경본을 검증한다.** 처음과 같은 기능 조건과 기존 호출 경로를 확인하되, 중간 검사 결과가 최종 변경본에 대한 재사용 기준을 만족하면 같은 검사를 반복 실행하지 않는다. 회귀가 생기면 방금 한 정리를 수정하거나 그 부분만 되돌리고 같은 입력으로 재검사한다. 사용자의 기존 수정과 완성된 기능을 보존한다. 정식 협업에서 제품 코드가 바뀌었다면 해당 변경분을 다시 코드 검토받고 영향을 받는 독립 테스트를 마친다. 일반 한글 주석만 바뀐 경우와 독립 테스트의 결과 재사용 판단도 위 기준을 따른다.

최종 코드 기준으로 로드맵을 갱신한다. 최근 작업 기록에는 무엇을 합치거나 옮겼는지(또는 그대로 둔 이유), 주석 점검과 전후 검증 결과를 짧게 적는다. 중단 시에는 ‘사용자 실행 확인 대기’, ‘사용자 만족 확인 / 구조 점검 대기’, ‘구조 정리 완료 / 주석 보완 대기’, ‘주석 정리 완료 / 재검증 대기’ 중 실제 지점을 남긴다.
