# 기획·설계에서 성공의 증거를 정한다

**기획**은 메인이 사용자와 “무엇이 되면 이 일이 끝났다고 할까?”를 정하는 일이다. **설계**는 그 결과를 만들 방법과 확인할 방법을 정하는 일이다. “기획만 해줘”라면 기획서를 저장해 보여주고, “설계까지 해줘”라면 설계서를 저장해 보여주는 데서 마친다. 메인은 초안을 검토자에게 보내기 전, 검토 의견이나 사용자 결정을 반영한 뒤에 같은 단계 문서를 갱신한다. [단계별 파일 위치](project-state.md#기획서와-설계서)

## 기획할 때 메인이 할 일

누가, 어떤 상황에서, 무엇을 할 수 있어야 하는지 사용자와 정한다. 코드나 문서에서 알 수 있는 사실은 메인이 직접 찾아본다. 답에 따라 결과가 달라질 때만 사용자에게 한 번에 1~3개씩 묻고, 추천하는 선택과 이유를 설명한다.

예를 들어 “메모를 저장해줘”라는 요청에서 앱을 껐다 켠 뒤에도 읽을 수 있어야 한다고 합의했다면, **완료 조건**을 “메모에 ‘우유 사기’를 입력해 저장하고 앱을 다시 열었을 때 같은 글이 보인다”라고 적는다. 나중에 누구든 같은 행동으로 결과를 판단할 수 있다.

업무 규칙의 해석이 갈리면 차이가 드러나는 입력과 기대 결과를 해당 완료 조건에 붙인다. 예를 들어 “보관한 메모를 기본 목록에서 숨긴다”면, 같은 메모를 기본 목록에서 볼 때와 제목으로 검색할 때를 비교한다. 기본 목록에서 숨기는 것은 확정이고 검색 동작이 이번 범위에서 미정이면, 기존 결정과 코드에서 확인한 뒤 남은 질문만 사용자에게 묻는다. 결정된 예시는 구현과 검증에서 그대로 쓴다.

새 프로젝트의 기획에서는 앱과 서버를 한 저장소에서 관리할지(모노레포), 각각 관리할지(멀티레포), 각 모듈에서 기능별·계층별 등 어떤 방식으로 코드를 나눌지 사용자와 정한다. 이미 정한 사항은 기획서에 결정과 적용 범위를 적거나 기존 구조 문서를 연결한다. 아직 선택해야 하고 이번 작업에 영향을 준다면 실제 배포·변경 단위를 기준으로 선택지와 이유를 설명한다. 기존 프로젝트에 기능을 추가할 때는 기록과 현재 코드에서 확인한 결정을 이어 쓴다. [프로젝트 구조 판단](project-layout.md)

범위와 영향이 명확한 단순 개발도 기획에서 시작한다. 메인이 원하는 변경·범위·확인 기준을 기획 채팅에 짧게 적고, 그 내용을 개발 서브에이전트에게 바로 전달한다. 기획 자체나 문서를 요청받으면 요청한 단계의 파일을 저장한다. [작업 경로와 승인](../SKILL.md#작업-경로와-승인)

정식 협업에서는 기획서에 목표, 이번에 할 일과 제외할 일, 완료 조건을 적는다. 조건마다 `AC-1`처럼 번호를 붙이면 나중에 담당자에게 같은 조건을 정확히 가리킬 수 있다. 기획 검토자는 조건들이 사용자의 원래 요청을 담고 있는지 확인한다.

## 현재 코드로 기획을 실현할 수 있는지 확인한다

설계를 맡은 메인이나 조사 담당자는 기획서의 완료 조건을 읽고 [코드 로드맵](code-map.md)에서 관련 기능을 찾는다. 실제 진입점에서 호출되는 코드, 저장 데이터의 형식, 사용하는 기능이나 권한, 관련 테스트를 필요한 만큼 따라간다. 설계서에는 중요한 조건별로 **현재 확인한 사실과 위치 → 필요한 변경 → 결과를 확인할 방법**을 적는다. 코드가 아직 없는 새 프로젝트라면 새로 만들 부분과 먼저 확인할 외부 조건을 적는다.

- **현재 기능으로 되거나, 허용된 변경으로 만들 수 있다.** 쓸 수 있는 기존 기능과 새로 만들 부분을 구분해 설계를 계속한다. 원하는 함수가 아직 없다는 사실만으로 기획을 돌려보내지 않는다.
- **자료가 부족하다.** 어떤 사실이 있어야 판단할 수 있는지 밝힌다. 먼저 코드·작은 표본·기존 테스트에서 확인하고, 그래도 모르면 그 조건을 미확인으로 남긴다. 실제 접근이나 정책 결정이 필요하면 메인이 필요한 정보만 요청한다.
- **현재 제약으로 요구를 충족할 수 없거나, 기획에서 정한 방법이 사용자 목표와 어긋난다.** 영향을 받는 설계와 구현을 멈춘다. 메인은 **어느 조건에서 어떤 문제가 생기는지, 근거가 어디 있는지, 기획을 어떻게 바꾸면 무엇을 얻고 잃는지, 무엇을 추천하는지** 설명하고 선택을 요청한다. 같은 결과를 제공할 수 있고 내부 구현 방법만 달라지는 경우에는 메인이 설계에서 해결한다.

예를 들어 “예전 메모의 정확한 작성일을 표시”해야 하는데 기존 파일에는 본문만 있다면 먼저 백업이나 다른 신뢰할 날짜 기록이 있는지 확인한다. 근거가 없다면 “기존 메모는 ‘작성일 미상’으로 표시하고 새 메모부터 기록”하는 안을 제안할 수 있다. 모든 기존 메모에 날짜가 꼭 필요하다면 믿을 수 있는 과거 기록을 가져오는 안과 그 비용을 함께 설명한다.

사용자 결정 전에는 원래 완료 조건을 유지하고 설계 초안과 최근 작업 파일에 막힌 조건·근거·제안·결정 대기를 남긴다. 결정이 오면 메인이 기획서의 해당 조건과 설계·검증 방법을 함께 갱신한다. 아직 구현을 시작하지 않은 정식 협업이면 최초 시작 지시를 따르고, 이미 구현 중이라면 아래 절차로 이어간다.

## 개발 중 기획이 바뀌면

단순 문구·값 수정이나 요청받은 Git 반영에는 아래 절차를 형식적으로 적용하지 않는다. 기존 기획·설계에 적힌 내용과 달라지면 관련 부분만 최소한으로 바로잡고, 문서가 없으면 새로 만들지 않는다. 값 하나라도 동작이나 데이터에 미치는 영향이 불명확하면 먼저 확인한다. 기능의 요구나 구현 방법을 다시 정해야 하는 변경이면 아래 절차를 따른다.

1. 메인은 바뀐 요구의 영향을 받는 작업을 잠시 멈추고, 이전 기준으로 일하는 담당자에게도 변경을 알린다. 결정이 명확하면 바로 반영한다. “결과가 마음에 안 들어”처럼 바꿀 결과가 불분명하면 그 차이만 묻는다.
2. 같은 작업의 **기획서**에 새 요구와 완료 조건을, **설계서**에 영향을 받는 동작·변경 위치·확인 방법을 먼저 반영한다. 작은 수정으로 시작해 두 문서가 없었다면 바뀐 부분 위주로 짧게 남긴다. 최근 작업 기록과 진행 중인 담당자의 지시도 새 기준에 맞춘다.
3. 개정한 기준으로 구현을 이어간다. 정식 협업에서는 기획·설계의 달라진 부분을 독립 검토받고 곧바로 개발하며, 구현 뒤 코드 검토와 독립 테스트를 거친다. 같은 작업의 변경 요청에 최초의 설계·구현 시작 지시를 반복하지 않는다. 이전 기준으로 도착한 결과는 새 조건과 대조한 뒤 사용한다.

사용자가 직접 실행한 뒤 기획을 바꿔 달라고 해도 같은 순서로 처리한다. 수정본을 테스트한 뒤에는 [사용자 실행 확인](verification.md#사용자가-직접-실행해-결과를-확인한다)을 새로 받는다. “지금은 기획서만 바꿔줘”처럼 단계를 제한했다면 지정한 문서에 결정과 보류된 단계를 남기고 마친다.

## 설계할 때 메인이 할 일

- 기존 코드에서 다시 쓸 기능과 바꿀 위치를 찾고 작업 순서를 잡는다. 각 작업은 그 결과를 따로 확인할 수 있을 만큼만 나눈다.
- 완료 조건마다 **어떤 상황에서 → 사용자가 무엇을 하면 → 무엇을 볼 수 있는지** 적는다. 판정에 필요한 화면이나 호출 방법, 권한, 입력값, 결과를 읽을 위치를 명시한다. 메모 예시에서는 앱을 다시 열어 글을 읽는 과정까지 설계한다.
- 성능이 요구된 경우에만 지표, 대표 입력과 규모, 비교할 동일한 측정 조건, 목표값 등 완료 기준을 정한다. [성능 검증](verification.md#성능이-완료-조건에-포함된-경우)
- 여러 기능을 거치는 흐름이나 오류 처리 방식이 달라져 설명이 어렵다면 실제 함수 이름으로 호출 순서를 짧게 그린다. 어디서 성공하고 어디서 실패하는지도 보여준다.

기획서·설계서와 단계별 검토가 모두 필요한 경우는 정식 협업이다. 설계 검토자는 각 작업이 합의한 결과에 필요한지, 결과를 실제로 확인할 방법이 있는지 본다. 설계와 구현을 시작할 시점은 [작업 경로와 승인](../SKILL.md#작업-경로와-승인)을 따른다.

## 기술적 선택을 따로 조사할 때

기존 메모 저장 기능을 그대로 연결하면 되는 경우에는 메인이 직접 설계한다. 기존 메모 파일을 계속 쓸지, 다른 저장 방식으로 옮길지에 따라 예전 메모를 열거나 복구하는 방법이 달라진다면 코드 조사가 필요할 수 있다. 이처럼 따로 조사할 기술적 선택이 있을 때만 메인이 **그 선택에 대한 질문**을 별도 설계 담당자에게 보낸다. [역할 인계](collaboration.md#역할-인계)

담당자는 확정 기획과 관련 코드를 직접 읽고 선택지, 추천 이유, 기존 데이터와 완료 조건에 미치는 영향, 확인 방법을 회신한다. 메인이 근거를 확인해 전체 설계를 정리한다. 이 선택으로 사용자에게 보이는 동작이나 합의한 작업 범위가 달라질 때는 메인이 사용자와 결정한다.
