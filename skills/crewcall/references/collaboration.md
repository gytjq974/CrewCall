# 역할을 추가하고 인계하는 법

사용자는 메인 채팅에서 원하는 결과를 말하고, 어떤 결과가 나오면 끝난 것으로 볼지 메인과 정한다. 일을 나눌 때는 메인이 각 과제의 담당자 한 명을 정한다. 메인이 직접 지시를 보내고 답을 받아 실제 문서나 코드와 맞는지 확인한다. 사용자는 하위 채팅을 오가며 메시지를 전달할 필요가 없다.

## 어떤 일을 누구에게 맡기나

개발 과제는 크기와 관계없이 개발 서브에이전트에게 보낸다. 같은 작업의 최신 맥락을 아는 개발 담당자가 있으면 이어 맡기고, 새 담당자가 필요하면 메인이 호출한다. 메인은 기획·설계, 읽기 조사, 결과 확인과 요청받은 Git 반영을 직접 할 수 있다. 필수 독립 검토·테스트는 작성에 참여하지 않은 담당자가 맡는다.

- **설계 조사**는 메인이 설계하다가 따로 살펴볼 기술적 선택이 생겼을 때 맡긴다. 담당자는 관련 코드와 제약을 확인해 선택지, 추천 이유, 확인 방법을 알려준다. 그 결과로 전체 설계를 정리하는 사람은 메인이다.
- **구현**은 제품 코드·설정·문구 등 제품 파일을 변경하는 일이다. 개발 담당자는 작업 폴더와 기존 변경을 확인하고 맡은 범위에서 구현한다. 버그는 [결함 조사 절차](debugging.md)에 따라 원인을 먼저 찾는다. 무엇을 어디서 고쳤는지, 설계와 달라진 점, 완료 조건별로 직접 확인한 결과와 남은 일을 보고한다.
- **테스트**는 실제로 기대한 동작이 나오는지 확인하는 일이다. 놓치기 쉬운 실패 사례, 별도 환경이나 권한, 독립적인 판정이 필요할 때 맡긴다. 담당자는 완료 조건을 읽고 기대 결과를 정한 뒤 검사할 코드와 기존 검사 결과를 확인한다. 빠진 사례는 필요한 테스트를 작성해 실행하고, 조건마다 통과·실패·미확인과 근거를 보고한다. 제품 문제라면 재현 방법과 기대한 값·실제 값을 메인에게 보내 구현 담당자가 고치게 한다. 테스트 자체의 오류는 테스트 담당자가 고친다. 수정 후에는 실패했던 사례와 수정의 영향을 받는 동작을 다시 확인한다.
- **검토**는 다른 사람이 만든 기획·설계·코드가 요청에 맞는지 읽고 판단하는 일이다. 단계별 필수 검토가 있거나, 다른 시각으로 살펴볼 구체적인 위험이 있을 때 맡긴다. 검토자는 요청받은 단계만 읽고 의견을 돌려준다. 수정은 작성자가 맡는다.

## 역할 인계

‘인계’는 다른 AI가 바로 일을 시작할 수 있도록 메인이 첫 메시지를 보내는 일이다. 메인은 인계할 단계의 스킬 지침을 실제 파일에서 읽고, 담당자가 착수 전에 직접 읽을 수 있게 선택된 `SKILL.md`와 관련 참조 파일의 경로·절을 전달한다. 기존 담당자에게 새 단계를 맡길 때도 해당 절을 확인한다. [단계 시작과 스킬 원문 확인](../SKILL.md#처음-시작하거나-이어받을-때)

**개발 지시는 메인이 작성한다.** 사용자의 말에서 원하는 결과를 추려, 확인한 현재 동작이나 관련 위치, 변경 범위, 유지할 제약, 완료 조건과 확인 방법을 필요한 만큼 알려준다. 요청에 없던 기능을 추측해 더하지 않는다. 결과를 가르는 미정 사항은 메인이 자료를 먼저 확인한 뒤 필요할 때만 사용자에게 묻는다. 저장소나 모듈을 맡길 때는 확인한 개발 패턴과 기획서·코드 로드맵의 관련 위치도 준다. 검토자도 같은 프로젝트 기준으로 구조를 판단한다.

| 담당자가 알아야 할 것 | 메인이 알려줄 내용 |
|---|---|
| 무엇을 맡았나? | 역할, 이번에 답할 질문 하나, 작업 폴더, 읽기만 할지 수정해도 되는지 |
| 무엇을 기준으로 하나? | 사용자 결정, 완료 조건, 제외한 일, 아직 모르는 점. 근거가 있는 파일·절과 검사할 변경본 |
| 무엇을 돌려주나? | 설계 조사라면 선택지와 근거, 구현이라면 변경 위치와 확인 결과, 검토라면 판정과 그 근거 |

예를 들어 사용자가 “메모 화면의 저장 버튼을 ‘메모 저장’으로 바꿔줘”라고 했다면, 메인은 기획 채팅에 “메모 화면의 저장 버튼 문구만 바꾸고, 기존 저장 동작도 확인하겠습니다”라고 정리한다. 개발 담당자에게는 확인한 버튼 위치와 함께 “표시 문구를 ‘메모 저장’으로 바꿔줘. 같은 화면에서 새 문구가 보이고 기존 메모가 저장되는지 확인해 결과를 알려줘”라고 보낸다.

저장 방식을 따로 조사하는 담당자에게는 다음과 같이 지시할 수 있다.

> 현재 메모 앱 프로젝트에서 저장 방식만 조사해줘. 확정 기획은 `plan.md`의 ‘오프라인 저장’, 기존 메모 표본은 `notes.json`에 있어. 앱을 다시 열었을 때 기존 메모를 그대로 읽어야 하고, 동기화는 이번 범위에서 제외했어. 파일을 읽고 JSON을 유지할 때와 SQLite로 옮길 때를 비교해줘. 추천 이유와 기존 메모가 보존되는지 확인할 방법을 알려줘.

**코드를 어디서부터 읽을지 알려준다.** 설계 조사·구현·테스트의 첫 메시지에 같은 프로젝트 로드맵의 경로와 이번에 볼 항목을 넣는다. 로드맵이 없는 단순 작업은 관련 파일과 변경점만 전달하며 인계 때문에 로드맵을 새로 만들지 않는다. 설계자는 기획과 실제 코드가 맞는지, 구현자는 영향을 받는 호출부와 변경 지점을, 테스트 담당자는 사용자 진입점과 관련 테스트를 먼저 본다. 담당자는 실제 파일과 다른 설명을 발견하거나 새 경로·테스트가 생기면 그 위치를 메인에게 알려준다. 메인이 변경 결과를 모아 공용 로드맵을 갱신한다. [코드 로드맵](code-map.md)

**근거 전달.** 설계 담당자에게는 저장한 기획서의 실제 경로와 해당 완료 조건을, 구현·테스트 담당자에게는 그 작업에 적용되는 설계서와 관련 조건을 보낸다. 간단한 기획만으로 개발할 때는 채팅에서 정리한 변경 범위와 확인 기준을 전달하고, 최근 작업 기록에 있으면 그 항목을 가리킨다. 새 담당자는 관련 프로젝트 원문을 직접 확인한다. 프로젝트 자료를 열 수 없으면 해당 부분만 발췌해 전달할 수 있다. 스킬 원문을 직접 읽어야 하는 경우는 위의 단계 시작 지침을 따른다. 긴 대화는 줄이되 결정·완료 조건·제외 사항·불확실한 점은 남긴다. 정식 협업이나 여러 세션에 걸친 인계에서는 완료 조건의 번호와 원문 위치를 함께 준다. 정식 협업에서 단계별로 건넬 자료는 다음과 같다.

| 맡기는 일 | 판단의 기준이 되는 자료 |
|---|---|
| 기획 검토 | 원래 사용자 요청, 사용자가 내린 결정, 기획 초안 |
| 설계 검토 | 검토를 통과한 기획서와 설계 초안 |
| 구현·테스트 | 현재 구현할 설계와 완료 조건. 개발 도중 기획이 바뀌었다면 새 결정이 반영된 기획서·설계서의 해당 부분 |

정식 협업 외의 작업을 이어갈 때는 사용자 요청과 합의한 완료 조건의 위치를 준다. 이미 `current.md`에 적혀 있으면 그 항목을 가리킨다.

**담당자 연결.** 역할을 맡길 때의 기본 수단은 기획 채팅에서 메인이 호출하는 서브에이전트다. 같은 작업의 기존 담당자가 역할과 독립성 조건을 충족하면 그 담당자에게 이어 맡긴다. 예전에 역할 채팅을 사용했던 프로젝트도 새 과제에는 이 기본값을 적용한다. 조사·감리·테스트에 사용자가 전용 채팅을 지정한 경우에도 메인이 직접 지시하고 회신을 받는다. 새 담당자에게는 첫 실제 과제와 함께 해당 역할 문서의 경로와 절을 보낸다. 개발 서브에이전트를 호출할 수 없으면 적합한 기존 개발 담당자에게 이어 맡기거나 일시적 장애를 해소한 뒤 재시도한다. 그래도 배정할 수 없으면 메인이 구현을 대신하거나 사용자에게 지시문 전달을 맡기지 않고, 기획 채팅에 ‘개발 담당자 배정 대기’와 사유를 알린다.

**결과 받기.** 메인은 누가 어떤 작업 폴더와 변경본을 맡았는지, 실제로 쓴 채팅 또는 에이전트와 그 ID를 기록한다. 진행 중인 일은 같은 ID의 담당자에게서 결과를 받는다. 후속 요청에는 달라진 내용과 이번 질문만 보낸다. 담당자가 묻는 사항은 저장소와 사용자 결정에서 먼저 답을 찾는다. 같은 파일을 동시에 고치는 담당자는 한 명으로 두고, 같은 검사를 여러 사람에게 중복해서 맡기지 않는다.

검사 결과는 한 곳에 **완료 조건 / 검사한 코드와 실행 환경 / 실행 명령 또는 확인 방법 / 결과값이나 근거 위치**를 남기고, 다른 기록에는 결과 요약과 그 위치를 연결한다. 아직 Git에 커밋하지 않은 수정이 재현에 필요하면 해당 파일과 달라진 부분도 검사 결과에 적는다. 필수 검토나 독립 테스트를 맡길 사람이 없으면 할 수 있는 일까지 진행하고 남은 단계는 대기로 보고한다. 구현자가 직접 확인한 결과는 자체 검사로 기록한다. 최종 판단과 사용자 보고는 메인이 맡는다.

**원인 조사를 나눌 때.** 기존 로그나 한 번의 검사로 원인 후보 여럿을 구분할 수 있으면 먼저 그 방법을 쓴다. 남은 질문들이 서로 독립적이고 각각 시간이 걸릴 때만 나눠 조사한다. 조사자는 답과 근거를 메인에게 보낸다. 원인만 요청받았으면 결과를 종합해 보고하고 마친다. 수정까지 요청받았으면 [작업 경로와 승인](../SKILL.md#작업-경로와-승인)에 따라 개발 서브에이전트가 고친다.

## 독립 검토

검토 대상의 작성에 참여하지 않은 담당자가 별도 대화에서 검토한다. 메인은 원래 요청, 합의한 범위와 제외 사항, 완료 조건, 검토할 기획서·설계안·코드의 실제 변경본을 준다. 필요한 제약과 이미 실행한 검사 결과에는 출처를 붙인다. 작성자가 기대하는 판정과 작성 당시의 대화 전문은 전달하지 않는다.

검토자는 단계에 따라 다음 질문에 답한다.

- **기획** — 사용자가 원한 결과가 완료 조건에 담겼는가? 사용자가 제외한 기능을 다시 넣지는 않았는가?
- **설계** — 제안한 작업이 각 요구를 충족하는 데 필요한가? 사용자가 원하는 동작을 확인할 방법이 있는가? 더 작은 변경으로 같은 목표를 달성할 수 있는가?
- **코드** — 실제 변경과 이를 부르는 코드를 보면 어느 입력이나 상황에서 기대와 다른 결과가 나오는가? 변경 때문에 기존 기능이 깨지거나 관련 보안 문제가 생길 수 있는가?

요구 누락, 범위 밖 기능, 지나친 복잡성, 구체적인 위험을 발견하면 **어디가 문제인지 → 사용자에게 어떤 영향이 있는지 → 최소한 무엇을 고칠지**를 알려준다. 요구 충족을 확인했고 문제가 없으면 ‘통과’, 고칠 부분이 있으면 ‘수정 요청’, 사용자 선택이 남았으면 ‘사용자 결정 필요’로 보고한다. 근거가 부족하면 해당 조건을 ‘미확인’으로 남기고 필요한 자료를 적는다.

중요한 코드 리뷰 의견은 작성자가 요구사항·호출부·테스트와 대조해 반영하거나 기존 동작을 유지할 근거를 메인에게 짧게 알린다. 메인이 지적을 확인하면 승인된 범위의 수정은 해당 개발 담당자에게 맡긴다. 담당자를 이어 쓸 수 없으면 메인이 후임 개발 서브에이전트를 정한다. 필수 독립 검토의 ‘수정 요청’에 이견이 있으면 검토자가 근거를 보고 재판정한다. 수정에 참여하지 않은 검토자가 수정분을 다시 확인하면 메인이 결과를 받는다. 독립 검토가 필수인데 작성자와 분리된 대화를 확보할 수 없다면 ‘독립 검토 대기’로 알린다.

독립 테스트에서 제품 결함이 나오면 메인이 재현 입력과 기대값·실제값을 개발 담당자에게 보내 수정을 맡긴다. 수정본에 필요한 코드 재검토를 받은 뒤 테스트 담당자에게 실패했던 조건과 영향 범위를 다시 확인시킨다. 메인은 같은 변경본에 대한 판정과 남은 미확인 사항을 기획 채팅에 모아 보고한다. 합의한 범위 안의 수정과 재검사는 메인이 이어서 진행한다.

## 역할별 모델과 추론 수준

기획을 비롯해 메인이 맡은 일은 현재 채팅의 설정을 쓴다. 다른 역할을 배정할 때는 모델과 추론 수준을 각각 정한다. 이번 작업에서 사용자가 지정한 값을 먼저 적용한다. 지정하지 않은 항목은 프로젝트 역할 문서의 **해당 역할 절 → 공통 절 → 아래 기본값** 순으로 찾는다.

| 역할 | 기본 모델 | 기본 추론 수준 |
|---|---|---|
| 설계 조사 | 현재 메인 설정 | 현재 메인 설정 |
| 구현 | `gpt-6.2-sol` | `medium` |
| 테스트 | `gpt-6.2-sol` | `low` |
| 검토 | `gpt-6.2-astra` | `medium` |

- **처음 호출할 때** 선택한 값을 도구 인자로 전달한다. `spawn_agent`에서 직접 지정할 때는 `fork_turns="none"`을 사용한다. 담당자가 이전 대화를 보지 않아도 시작할 수 있게 첫 요청에 역할 인계 내용을 담는다.
- **같은 작업을 이어갈 때** 후속 작업과 재검토에는 기존 설정을 쓴다. 사용자가 새로 지정한 값은 지정한 기간에 적용한다. 예를 들어 “이번 검증만” 지정했다면 검증이 끝난 뒤 이전 설정으로 돌아간다.
- **담당자를 바꿀 때** 현재 담당자에게 새 설정을 적용할 수 있으면 그대로 맡긴다. 교체가 필요하면 기존 요청의 상태와 결과를 먼저 확인하고 남은 일만 인계한다.
- **지정한 값을 사용할 수 없을 때** 어떤 값이 지원되지 않는지 알린다. 사용자가 필수로 지정한 값은 대체하기 전에 확인한다. 기본값만 쓸 수 없는 경우에는 가능한 설정으로 진행하고 실제 선택을 보고한다.
