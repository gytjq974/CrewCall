# CrewCall

CrewCall **0.9.9**는 AI와 함께 기획·설계·구현·테스트를 진행하는 개인 개발 스킬이다. 단계별 개발로 품질과 요구된 성능을 확인하고, 로드맵과 기록을 이어 써 필요한 코드만 읽는 것을 목표로 한다. 이 저장소에서 스킬을 만들고 개선하며, 다른 프로젝트에서 사용할 지침은 `skills/crewcall/`에 모여 있다.

**처음 읽는다면** [SKILL.md 첫머리의 메모 앱 예시](skills/crewcall/SKILL.md#crewcall)부터 읽는다. 기획·설계·완료 조건이 각각 무엇인지 한 가지 요청으로 살펴볼 수 있다. **작업 방식을 고치러 왔다면** [바꾸고 싶은 행동으로 파일 찾기](#바꾸고-싶은-행동으로-파일-찾기)로 바로 간다.

## 처음 읽는 순서

1. **누가 어떤 결정을 맡는지 본다.** ‘메인’은 나와 대화하며 결과를 책임지는 AI다. 기획은 내가 메인과 직접 정한다. 설계도 메인이 맡고, 따로 조사할 기술적 선택이 있을 때만 그 질문을 별도 역할 채팅에 맡긴다. 작은 수정은 메인이 바로 구현하고 확인한다. 정식 협업에서는 기획 검토 후 내 설계 시작 지시를, 설계 검토 후 내 구현 시작 지시를 기다린다. [작업 경로와 승인](skills/crewcall/SKILL.md#작업-경로와-승인)
2. **실제 요청 두 개를 비교한다.** [검증 사례](evals/scenarios.md)에서 E-01 ‘기획만 요청’과 E-02 ‘작은 기능 수정’의 입력과 기대 행동을 읽는다. 전자는 기획에서 끝나고 후자는 수정한 동작까지 확인한다.
3. **직접 적용해 본다.** 아래 [사용 예](#사용-예)에서 작업 폴더와 원하는 결과를 내 프로젝트에 맞게 바꾼다.

## 역할 채팅에는 무엇을 보내나

메모 앱을 만든다면 나는 “내 기기에서 오프라인으로 쓰고, 다시 열면 메모가 남아야 해”라고 설명하면 된다. 메인이 나와 완료 조건과 제외 범위를 정한다. 기존 저장 방식으로 충분하면 메인이 설계하고, 파일 저장과 데이터베이스 중 어느 쪽이 기존 메모를 호환하는지 조사가 필요하면 그 선택을 맡긴다.

이때 **담당자가 읽을 지시문은 메인이 직접 써서 전달한다.** 설계 담당자에게는 확정 기획의 해당 절, 기존 저장 코드 위치, 비교할 질문과 돌려받을 결과를 보낸다. 구현 담당자에게는 합의된 설계와 바꿀 범위, 확인할 완료 조건을 보낸다. 긴 대화는 필요한 결정만 추려 전달하고, 담당자가 원문을 직접 읽을 수 있는 위치를 함께 준다.

독립 검토를 맡길 때는 산출물을 작성하지 않은 별도 채팅에 원래 요청과 실제 산출물을 전달한다. 검토자는 요구 누락, 범위 초과, 검증의 빈틈을 직접 대조한다. 예를 들어 한 기기에서 쓸 메모 앱의 설계에 계정 가입이 추가됐다면, 어떤 사용자 결정과 어긋나는지 짚고 그 기능을 덜어내는 수정을 제안한다.

## 프로젝트의 구조는 누가 정하나

새 프로젝트라면 기획할 때 메인과 함께 저장소 구성과 개발 패턴을 정한다. 예를 들어 “웹과 API는 별도 저장소로 관리하고 각각 기능별로 묶자”고 정하면 메인이 기획서에 남긴다. 다음 설계 채팅도 웹의 검색 화면과 API의 검색 처리를 각 저장소의 검색 기능에 배치한다.

기존 프로젝트라면 이미 쓰는 방식을 이어간다. 웹과 API가 한 저장소에 있고 API가 컨트롤러·서비스·저장소 계층으로 나뉘어 있으면 새 검색 기능도 그 계층을 따른다. CrewCall의 예시 경로나 일반 권장 패턴이 달라도 그 이유로 재편하지 않는다. 프로젝트 구조를 바꿔야 할 실제 제약이 발견되면 메인이 근거와 대안을 설명하고 사용자가 결정한다. [프로젝트 구조 판단 지침](skills/crewcall/references/project-layout.md)

## 설계하기 전에 어느 코드를 살펴보나

기획이 정해지고 설계를 시작할 수 있으면, 설계안을 쓰기 전에 메인이 대상 프로젝트의 **코드 로드맵**을 준비한다. 기본 위치는 `docs/workflow/code-map.md`다. 이미 코드 구조와 테스트 위치를 정리한 문서가 있다면 그 문서를 쓴다. 로드맵에는 프로젝트의 주요 기능, 실행이 시작되는 곳, 데이터가 오가는 경로, 관련 테스트가 정리된다. 새 설계·구현·테스트 채팅은 메인이 가리킨 로드맵 항목부터 읽고, 실제 코드와 테스트를 열어 판단한다. 구현과 테스트가 끝나면 바뀐 경로와 검사 방법을 같은 로드맵에 반영한다. 다음 작업도 그 문서에서 시작한다. [코드 로드맵 지침](skills/crewcall/references/code-map.md)

예를 들어 “예전에 쓴 메모에도 정확한 작성일을 표시해줘”라고 했다고 하자. 설계 담당자는 로드맵에서 저장 코드를 찾고, 실제 저장 형식과 기존 파일에 작성일이 남아 있는지 확인한다. 날짜를 복원할 근거가 없다면 메인은 **어느 완료 조건이 왜 막히는지** 설명하고 “기존 메모는 ‘작성일 미상’으로 표시하고 새 메모부터 기록하자”처럼 수정 방향과 이유를 제시한다. 사용자가 선택하면 그 결정을 기획서에 반영하고 해당 설계를 이어간다. 요구를 그대로 충족하는 다른 구현 방법이 있으면 설계에서 해결한다. [기획·설계 지침](skills/crewcall/references/planning.md)

### DB를 쓰는 프로젝트에서 테이블 관계 찾기

예를 들어 메모가 어느 폴더에 속하는지 알아보려면 코드 로드맵의 저장 항목에서 **현재 DB 구조를 담은 SQL 파일(DDL)**을 연다. `notes.folder_id`가 `folders.id`를 참조한다면 그 관계를 외래 키 정의에서 확인할 수 있다. 프로젝트에 이미 전체 구조를 담은 SQL 파일이 있으면 그 파일을 쓰고, 없으면 기본적으로 대상 프로젝트의 `docs/workflow/schema.sql`에 만든다.

새 테이블이나 컬럼을 제안할 때는 설계서에 SQL 초안으로 남긴다. 실제로 구현하면 현재 DDL을 갱신하고 검증해 다음 채팅이 같은 파일을 이어 쓸 수 있게 한다. [데이터베이스 DDL 지침](skills/crewcall/references/database-schema.md)

## 개발을 마치고 코드를 정리하는 시점

문구 한 곳이나 의미가 분명한 설정값 수정, 요청한 커밋·푸시처럼 단순한 작업은 기획·설계 없이 바로 처리하고 필요한 확인 뒤 결과를 알린다. 메인이 짧게 끝낼 수 있으면 직접 하고, 최근 구현 담당자가 관련 코드를 이미 파악해 더 적은 재확인으로 이어갈 수 있으면 그 담당자에게 맡긴다. 아래의 전체 개발 절차를 단순 작업마다 새로 시작하지 않는다. [작업 경로](skills/crewcall/SKILL.md#작업-경로와-승인)

작은 수정을 메인이 혼자 했든, 여러 담당자가 함께 개발했든 순서는 같다. 개발과 필수 테스트가 끝나면 메인은 **사용자가 직접 실행할 방법과 기대 결과**를 알려주고 답을 기다린다. 예를 들어 메모 웹 앱이라면 실제 접속 주소를 주고 “메모에 ‘장보기’를 쓰고 저장해 보세요. 탭을 닫고 같은 주소를 다시 열었을 때 목록에 ‘장보기’가 남아 있나요?”라고 안내한다. [검증 지침](skills/crewcall/references/verification.md)

개발 도중이나 직접 써 보는 중에 “빈 제목은 목록에서 ‘제목 없음’으로 보여줘”라고 기획을 바꿀 수 있다. 메인은 **기획서**에 새 요구와 완료 조건을, **설계서**에 목록 표시 방식과 테스트 기준을 먼저 반영한다. 이미 시작한 개발이므로 별도의 시작 지시를 기다리지 않고 목록을 고쳐 테스트한다. 그런 다음 빈 제목으로 저장한 메모가 어떻게 보이는지 사용자가 새 결과를 직접 확인할 방법을 안내하고 답을 기다린다. “지금은 문서만 고쳐줘”라고 했다면 두 문서를 갱신한 곳에서 멈춘다. [기획·설계 지침](skills/crewcall/references/planning.md)

사용자가 직접 써 보고 **“이제 원하는 대로 보여. 이 결과에 만족해”**라고 답하면 메인이 구조 점검을 시작한다. 예를 들어 목록의 여러 화면이 빈 제목을 똑같이 처리한다면 기존 표시 함수를 함께 쓸 수 있다. 내보낸 파일에서 빈 칸을 보존해야 한다면 그 처리는 따로 둔다. 필요한 구조 정리 뒤에는 함수 역할, 분기의 업무상 의미, 중요한 처리 이유를 짧은 한글 주석으로 보완한다. 이름과 코드만으로 충분한 설명은 생략하고 함수마다 긴 설명을 붙이지 않는다. **구조를 그대로 두더라도 필요한 주석까지 점검해야 리팩토링 완료다.** 최종 변경본에서 사용자가 확인한 동작을 다시 테스트하고, 달라진 코드나 테스트 위치를 로드맵에 남긴다. [최종 리팩토링 지침](skills/crewcall/references/refactoring.md)

파일을 둘 곳은 앱마다 다르다. 메인은 각 모듈에서 실제로 소스를 읽는 빌드 설정과 팀 지침을 먼저 확인한다. 예를 들어 서버가 Maven의 기본 경로를 재정의했다면 그 설정을 따르고, 웹 앱에서는 페이지를 옮길 때 기존 URL이 유지되는지 확인한다. 한 번 확인한 규칙은 근거 파일과 함께 해당 프로젝트의 로드맵에 남긴다. [개발 환경별 디렉터리 규칙](skills/crewcall/references/project-layout.md)

## 디렉터리별 역할

| 위치 | 무엇이 들어 있고 언제 여는가 |
|---|---|
| 저장소 루트 | 이 README는 사람이 읽는 안내서다. AGENTS.md는 AI가 **CrewCall 자체를 개발할 때** 읽는 지침이다. |
| `skills/crewcall/` | 다른 프로젝트에 적용할 스킬 전체다. AI는 SKILL.md에서 시작해 작업에 필요한 상세 지침을 찾아간다. |
| `skills/crewcall/references/` | 기획·설계, 코드 로드맵 작성, 역할 협업, 결함 조사, 검증, 작업 인계 지침이 있다. 지침에 따라 작성하는 프로젝트 로드맵과 역할·진행 기록은 **대상 프로젝트**에 둔다. |
| `skills/crewcall/agents/` | openai.yaml에 스킬의 표시 정보를 둔다. 역할별 모델을 바꾸는 위치는 references/collaboration.md다. |
| `docs/` | [development.md](docs/development.md)에 피드백, 수정 이유, 실제 평가 결과를 기록한다. [0.9.1 변환 검증 기록](docs/crewcall-0.9.1-verification.md)은 첫 버전을 만들 때 원래 프롬프트의 규칙을 빠짐없이 옮겼는지 확인한 자료다. |
| `evals/` | [scenarios.md](evals/scenarios.md)에 평가용 요청과 기대 행동이 있다. 지침을 바꾼 뒤에는 해당 요청으로 시험하고, 관찰한 결과를 docs/development.md에 남긴다. |

## 새 채팅에서 이전 작업 이어가기

이 저장소의 [최근 작업](docs/workflow/current.md)에서 이어갈 일을 보고, [실제 코드 로드맵](docs/workflow/code-map.md)에서 관련 지침과 평가 위치를 찾는다.

개발 중인 **대상 프로젝트**에서 `docs/workflow/current.md`를 열면 최근 작업, 현재 단계, 완료한 일, 기다리는 결정, 다음 행동이 보인다. 그 안의 링크로 작업별 기획서(`tasks/<작업명>/plan.md`)와 설계서(`design.md`)를 읽는다. 기존 프로젝트에서 이미 쓰는 문서가 있으면 그 경로가 표시된다.

새 채팅도 같은 작업 폴더와 변경본을 열고 “CrewCall로 이어서 해줘”라고 하면 된다. 스킬을 아직 설치하지 않았다면 아래 예시처럼 스킬 파일의 경로를 함께 준다. 이전 메인이 설계 검토까지 마치고 구현 시작 지시를 기다리던 상황이라면, 새 메인도 그 지점에서 기다린다.

## 사용 예

현재 로컬 소스를 적용하려면 스킬 파일과 **실제로 작업할 프로젝트**를 함께 지정한다. 아래의 MyPracticeProject는 예시이므로 내 프로젝트 경로로 바꾼다.

> C:/dev/CrewCall/skills/crewcall/SKILL.md를 읽고 적용해줘. 작업 대상은 C:/dev/MyPracticeProject야. 개인용 할 일 앱의 요구사항을 정리하고 기획만 해줘.

설치 후 환경에서 스킬이 발견되면 다음처럼 이름으로 호출할 수 있다. 로컬 스킬로 실행한 사례와 결과는 개발 기록에서 확인한다. [실행 결과](docs/development.md#행동-평가-결과)

> $crewcall 현재 프로젝트에서 이 버그의 원인을 조사하고 수정·검증해줘.
